# 场景解读适配规范（双端通用 + 后端契约）

> 适用 iOS / Android 客户端 + quickread 后端（readout-desktop）。与 `划重点批注-场景化需求.md`、`高亮与mark颜色统一规范.md` 配套。
> 版本：2026-06-26。

## 0. 一句话

**content_type（6 场景）和 depth（3 档深度）是两条正交轴**：场景只改「划什么/怎么批/语气」，深度只改「详略/长度」。后端 prompt 用「**明确目标 → 定义工具 → LLM 决策**」组织，不写硬规则。**content_type 缺省时后端行为与今天完全一致**（保护扩展端线上 3 档深度服务）。

---

## 1. 正交模型

| 轴 | 控制什么 | 来源 | 取值 |
|---|---|---|---|
| **content_type** | 划什么 · 批注侧重 · 语气 · 用哪种标注 · weight/role | 首页场景入口（移动端） | `paper` `book` `report` `contract` `study` `manual`；**nil = 通用** |
| **depth** | 详略 · 长度 · 块数 / mark 密度 | 用户设置（3 档） | `overview` `standard` `deep` |

**铁律**：depth 永远跟随用户设置；**content_type 绝不改 depth**。两轴独立 → 同一篇论文可用「速览/标准/深入」三种详略来讲，划的重点和批注口吻不变。

---

## 2. 硬约束：不影响扩展端线上 3 档深度服务

quickread 后端是**扩展端（readout-desktop）与移动端共用**。扩展端**没有 6 场景、只发 depth、不发 content_type**。因此：

- `content_type` **缺省（扩展端 + 移动端通用导入）→ 后端走与现在完全相同的 3 档深度逻辑，一字节不改**。
- 6 场景分支**仅在 content_type 存在时叠加**：`if content_type 存在 → 叠加该场景的目标段；else → 现有 prompt 原样`。
- depth 字段语义/取值/默认行为对扩展端**保持不变**。
- 回归基线：「content_type 为空 == 今天的输出」，用扩展端现有用例验证不回归。

---

## 3. 指导原则：明确目标 → 定义工具 → LLM 决策

prompt 与本规范**不写「论文必须用圈、合同必须用波浪」这类硬性映射**，而是：

### 3.1 ① 明确目标（每个 content_type 一句解读目标）

> 给 LLM 的是「这次解读要让读者获得什么理解」，不是划什么的清单。

| content_type | 解读目标（让读者…） |
|---|---|
| `paper` | 理解这篇研究**解决什么问题、用什么方法、关键结论与贡献、有何局限**。 |
| `book` | 把握**核心观点、脉络与本章主旨、关键概念与转折**。 |
| `report` | 抓住**核心结论、关键数据的含义、以及风险提示**。 |
| `contract` | 看清**自己的权利义务、关键金额/期限、以及对自己不利或有陷阱的条款**。 |
| `study` | 掌握**知识点与定义、易考点，并有通俗解释与记忆点**。 |
| `manual` | 不漏**关键步骤与警告，理解关键参数的作用**。 |
| `null`（通用） | 综合判断，帮读者抓住要点（= 今天的通用解读）。 |

### 3.2 ② 定义工具（统一工具箱，所有场景共用；只定义语义，不规定何时用）

**标注动作（action）语义：**

| action | 语义 |
|---|---|
| `highlight` | 马克核心句（荧光笔） |
| `underline` | 强调 |
| `wave` | 风险 · 警示 |
| `circle` | 术语 · 生词 · 关键实体 |
| `star` | 亮点 · 金句 |
| `number` | 步骤序号 |

**重要度（weight）语义：** `primary`=核心（粗笔） · `secondary`=支撑 · `tertiary`=次要（细线）。
**角色（role）语义（透传，供客户端可选着重）：** `key` · `caution` · `term` · `example`。

> 这套工具箱正是客户端已实现的渲染能力（见 §5）。

### 3.3 ③ LLM 决策

给定「**目标 + 原文**」，由 **LLM 自主决定**：划哪些 span、各用什么 `action`/`weight`/`role`、批注怎么写。**不得在 prompt 里硬编码「某场景必须用某 action」**。与快道质道承接 prompt 的「目标驱动」一致。

---

## 4. depth 三档语义（只调详略，不改划什么）

| depth | 含义 |
|---|---|
| `overview`（速览） | 只讲主干、最少 mark；块数少、批注短。 |
| `standard`（标准） | 常规详略与 mark 密度。 |
| `deep`（深入） | 细节 + 局限 + 延伸；块数/批注更多、mark 更密。 |

同一 content_type 下，depth 只改「讲多深/多长/标多密」，**不改划什么对象、不改语气定位**。

---

## 5. 客户端契约

- extract-plan / fast-block0 请求**永远同时发** `content_type` + `depth`：
  - `depth` = 用户设置的 3 档（`AppSettings.explainDepth` / Android 等价）。**客户端不按场景改 depth。**
  - `content_type` = 当前场景 id；通用导入为 `null`（字段省略）。
- 未知 / 缺省 content_type → 后端降级通用、**零回归**。
- **客户端是通用渲染器**：按后端发来的 `action`/`weight`/`role` 渲染，**不含任何按场景的硬编码**（符合 §3 原则）。

> iOS 实现：`ExplainViewModel.requestDepth`（恒 = `settings.explainDepth`）、`buildPlanRequest`/`fastBlock0` 同时发 `content_type: scenario`。

---

## 6. 渲染契约（客户端，已就位）

- `weight` → 笔触粗细倍率（primary 1.6 / secondary 1.0 / tertiary 0.65）。
- `action` → 手写形状（highlight/underline/wave/strike/circle/star/number）。
- `role` → 语义透传（可选着重，默认不改色）。
- **颜色统一跟随 `highlightColorHex`**，不按场景/role 改色相（见 `高亮与mark颜色统一规范.md`）。

iOS 三端渲染已实现：`Views/Reader/MarkOverlay.swift`、`Views/Reader/PDFReaderView.swift`、`WebReader/src/mark-renderer.ts`（`HandwrittenMark.weightMultiplier`）。

---

## 7. 跨端一致性清单

- [ ] iOS / Android 两端**发送字段完全一致**：始终发 `depth`(用户设置) + `content_type`(场景或 null)。
- [ ] **后端是差异化唯一来源**：按 §3 的目标+工具箱组织 prompt；content_type 为空时不改动。
- [ ] Android 渲染对齐 P1：支持 `wave`/`star`/`strike` + `weightMultiplier`（与 iOS 倍率一致）+ role 透传。
- [ ] Android 客户端**不**按场景覆盖 depth（与本规范一致）。
- [ ] 后端接入后回归：content_type 为空 == 上线版输出；paper vs contract 进入差异明显，而 depth 切换只改详略。

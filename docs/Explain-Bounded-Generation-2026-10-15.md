# Explain bounded generation

Implementation notes for the 1.2.51 candidate. The final release report owns live synthesis, real-device and store status; the isolated test evidence below is not a live-service claim.

`ExplainViewModel` now wraps its injected/default speech generator with the same `AudioPlayerService.speechGeneration` controller as Read. Pausing before the first media item pauses the retained producer, aborts its HTTP attempt and resumes with the same request identity, without starting another plan. Generated but not-yet-queued narration has an explicit audio reservation, so prepared blocks and next-page payloads count toward the same audible budget. Queue promotion releases that reservation; actual audio identity prevents double counting.

Incremental narration still publishes audio together with its timed marks. A short narration unit, or a section that requires whole-section server composition, can finish one atomic unit past the watermark. Such a unit is bounded to 2,400 Unicode scalars and each network input still passes the shared 560/160 UTF-16 window. Oversized malformed sections fail before TTS; text and marks are never silently truncated. Atomic work bypasses only the buffer gate after admission, never pause, cancellation or serial transport. The shared controller holds one atomic owner until the consumer records its audio, including across higher-priority arrivals, and releases it on completion/error.

A current audible block may request a bounded refill when the playable queue falls to 10 seconds or less even if an unadopted future page already reserves 30 or more seconds. Its predicate checks the active playback owner, content generation, selected voice and requested/current block; detached preparation also checks the current or explicitly adopted page job. Future reservations remain counted and do not acquire this permission from nominal request priority. Pause and the globally unique atomic/transport owners still apply.

Background block preparation has stored task handles and per-task owner identities. Stop/content replacement cancels them; late callbacks cannot remove a replacement task at the same block index. Voice replacement retires old background owners. Next-page preparation retains its plan and source text, but only its first explanation block may be synthesized before adoption; the same successor producer waits for adoption and then obeys the shared budget.

Resume distinguishes a retained foreground producer from cached narration that still needs queue installation. Only an actual planning/streaming/voice-switch owner resumes in place; cached narration uses the existing ownership recovery/revoice path. If a pending Explain session still sees an outgoing Read queue, an explicit transport action claims an empty queue before controlling generation. This avoids both replaying the old mode and leaving the new producer blocked by the old queue's ownership.

## Kindle source-horizon review

The existing sentence source path normally prepares the next readable page, separately from TTS. `fulfilKindleSentenceDemand` can inspect up to three successors only when no new complete speech unit exists, for empty pages or a sentence spanning several pages; the startup path can likewise inspect three total pages. `prepareKindleSentencePage` performs source/OCR/overlay work, not paid audio generation. This is a bounded source exception, not an absolute two-page source guarantee. Reducing the loop to one successor without adding a safe sentence carry/projection would produce `noText` failures or broken cross-page sentences. No Kindle source-horizon code was changed in this Explain patch.

The later `future-budget.log` adds an actual prepared-future-Explain + current-Explain case: an unadopted 35-second opening remains reserved while the current block becomes audible, and the current speculative successor stays blocked once 15 seconds are playable. The shared controller also covers a consumed current prefix, a higher-priority future waiter, unknown-duration reservations, and pause before refill. See the report rollup for final-source reruns.

## Paused voice replacement

A replacement producer retains its ownership and exact continuation while paused. Its presentation no longer says “Preparing next section” or leaves the global switching banner active when admission is intentionally paused. The explicit Play action resumes the same producer; a later Pause still wins over installation. Focused tests cover pause-before-switch and pause-during-switch, no new requests while paused, late-response rejection and resume without a second explanation plan. Seven Explain generation cases pass in `reports/mobile-release-20261015/explain-paused-switch-final.xcresult`; the unrelated cold WebView fixture timeout in that combined run was repaired and its two affected pagination cases passed separately.

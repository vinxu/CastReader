# Kindle 离线阅读：方案重审与迭代计划

日期：2026-09-12。状态：方案评审稿；本轮只检索文档、历史讨论和代码，未修改应用代码、未构建或安装。

目标：用户在 CastReader 中打开正在读的 Kindle 书，主动保存到本机，随后即使断网、重启 App，也能从原进度继续看书、听系统 TTS，并获得与朗读对应的高亮和翻页。

## 1. 推荐结论

采用 **本机书籍副本 + 本机文字识别 + 系统 TTS 直接播放**。

- 产品目标保留“保存整本正在读的书”。当前页组仅作为中间验证和部分可用能力，不能包装成整书下载。
- 保存内容以“原页图片 + OCR 文本 + 词框 + 页序与位置映射”为第一版基线。这样可以保留原排版、插图，以及识别错误时的核对依据。
- 优先准备当前阅读位置及后续内容；完整覆盖校验通过后，才显示“整本已保存”。
- 系统 TTS 在阅读时直接出声，不预生成整本音频，不引入 Kokoro 模型或云端高品质音频下载流程。
- 把“页已保存”“可以看”“可以朗读”“整本完整”分别判断。图片完整但某页识别失败时，仍能看该页，不能假装该页已经可以朗读。
- 最先验证整书采集和位置副作用，其次验证系统语音同步。大规模移植、完整界面和性能优化建立在这两项事实之上。

整书采集尚不能作无条件承诺：已有实现证明了局部页面保存，历史扩展证明了逐页采集的工程路径；当前 iOS 对不同真实书籍的完整覆盖、Page Flip 可用性、Amazon 进度影响仍需实测。

### 2.2 已有原型实际做到哪里

原型通过 `captureVisiblePage` 保存当前页，再调用 `captureCandidatePages(afterKey:limit:12)` 获取候选后续页。它没有从书首走到书尾的采集状态机，也没有证明整书覆盖。

“13 页”是该原型的应用层上限，不是 Kindle 的固定整书分页协议。近期渲染资源可能包含前页、后页、不同尺寸、重复渲染；扩大数组上限不会得到完整书籍。

`OfflineReadingCacheStore` 的摘要和资源校验，证明的是“这些已保存字节自洽且未损坏”，不能证明“Amazon 原书一页没漏”。两种完整性都要实现。

原型的系统语音已有真实合成测试代码；历史任务报告过模拟器测试通过。本轮没有重新执行，也未找到足以证明当前 iOS 全书 Page Flip 路径可发布的真机验收记录。

### 2.3 历史扩展能借鉴什么

扩展历史提交 `7bdf0e0` 包含 `src/core/kindle-library-sync.ts`，`92d2274` 删除了该文件。可在 `/Users/xuxuheng/Documents/MyProject/readout-desktop` 的 git 历史中查看。

历史路径是：定位书首 → 实际翻页 → 图片暂存 IndexedDB → OCR → 章节文本送入 Live Session。手机接到的是文本，未构成带原页、词框和本地进度的原生离线书。

本次直接查看历史代码，确认不能沿用的判据包括：整数进度 `>=99%` 当书末、翻页超时继续触发翻页、用 Blob URL/百分比变化判断翻页、连续空 OCR 页提前结束、启动时清空 IDB。这些会导致漏页、重翻和断点丢失。

可复用的是“逐页确认、落盘与 OCR 分阶段、独立采集任务”的思路；历史耗时不能当作当前 iPhone 的性能基线。

### 2.4 本次修正旧讨论中的结论

1. “每 13 页一批循环就能整书”不成立；必须先证明每一页对应的源位置与顺序。
2. “Page Flip 在 Kindle App 有，就能在 WebView 枚举整本”未被证明。Amazon 公开说明主要列举 Kindle 设备和原生 App，不能据此推出当前 Web Reader 具备同等接口。[Amazon Page Flip 说明](https://kdp.amazon.com/en_US/help/topic/GNY87A6WM6EK6YEE)
3. “下载完跳回原页，所以不改变进度”不成立。Amazon 可能已同步采集期间的位置或最远已读点；本地恢复无法证明服务端副作用被撤销。
4. “只存图片，OCR 留到断网后”技术上可探索，但会把识别失败和等待留给出行用户。正常保存流程应同时完成 OCR；仅图片状态可以先看，并单独标明朗读未就绪。
5. “系统 TTS 有回调，所以必然等同云端精准词时间戳”不成立；要验证具体声音、语言和回调范围。不能用估算时间戳伪装成准确对齐。
6. “缓存层通用，因此只改入口即可支持全书和所有平台”不成立；当前整本 `ReadingDocument` 载入方式、播放器控制语义和权限来源都需要增量适配。

## 3. 用户体验与范围

### 3.1 主流程

1. Kindle 阅读器的“更多”增加“保存到本机”，书架的书籍菜单提供同一入口。
2. 默认目标“整本书”；说明“优先准备当前进度之后的内容”。另提供“从当前位置到结尾”，明确这不是整本。
3. 面板显示保存范围、已有覆盖、实际占用/估算占用，以及“本机系统语音”。高级格式和采集驱动不出现在普通用户流程。
4. 用户开始后，先持久化当前阅读锚点和已确认当前页，再按已验证的采集驱动准备后续内容。
5. 已提交的连续页面可提前阅读；状态显示“已保存 N 页，仍在准备”，以及“从当前位置可连续朗读约 X 分钟”。分钟数是基于已识别文字的估算，不能替代覆盖证据。
6. 完整校验通过，显示“整本已保存，可离线阅读”；本机音色和全书可读文字均就绪时，补充“可离线朗读”。
7. 飞行模式重新打开时，直接走本地封面、索引、页面、进度和声音。无需加载 Kindle 网站、重新做 session preflight 或等待订阅网络请求。
8. 恢复联网后继续当前离线会话。用户主动选“返回在线 Kindle”时才切换，并处理位置映射。

第一版保存时保留前台进度页；切后台或锁屏时可暂停采集。后续只有证明 WebView 在其他 App 页面后面仍能可靠渲染，才承诺“可在 App 内继续浏览其他页面”。离线听书的锁屏支持与网页采集的后台支持分别验收。

### 3.2 状态和文案

| 真实状态 | 用户可见状态与操作 |
|---|---|
| 尚无内容 | 保存到本机 |
| 不具备全书采集条件 | 暂只能保存当前可用页面；明确范围，不展示可执行的“整本下载” |
| 有 N 页、总量未知 | 已保存 N 页，正在确认后续内容；不显示整书百分比 |
| 部分连续内容就绪 | 已保存部分，可先阅读；继续保存 / 暂停 |
| 全部图片已保存，存在 OCR 问题 | 整本可看，部分页面暂不能朗读；本机重试识别 |
| 缺少合适的本机语音 | 内容已保存；需要准备本机语音才能朗读；提供试听与设置指引 |
| 全范围内容和声音就绪 | 整本已保存，可离线阅读与朗读 |
| 中断 | 已暂停及具体原因，保留完成量；继续保存 / 删除未完成内容 |
| 单页损坏 | 第 N 个离线页面需修复；其他完整页面仍可打开 |
| 权益过期 | 已保存内容保留；提示恢复 Pro，仍可查看占用和删除 |

“暂停”保留断点；“删除未完成内容”才释放这些资源。更新失败不影响之前完整的离线版本。系统音色不可用不阻止先保存页面。

### 3.3 首版边界

- iOS Kindle 优先；下载是既有讨论中的 Pro 功能。
- 支持原页阅读、同步高亮、自动翻页、句子导航、速度/音色切换、持久化恢复、睡眠定时。
- Aa：原页支持缩放；文字视图支持本地重排、字号和行距，前提是该页文字顺序已通过质量判断。离线调整不改变 Kindle 网页版式。
- 目录仅对已验证的章节锚点可跳转；未保存章节显示状态。目录不可得时提供“离线页面 N”，不把内部页序标成纸书页码。
- 首轮整书验收聚焦普通横排文字书；日文竖排、RTL、漫画、复杂双栏/表格按各自证据放行。未通过的书可保留原图阅读，不宣称可靠全书朗读。
- 离线解读需要额外本地 LLM 或已有讲解内容，本轮不纳入。离线状态点击解读应明确说明需要联网，不能自动发送原文。

## 4. 内容应该保存成什么

| 方案 | 价值 | 代价 | 决策 |
|---|---|---|---|
| 只存文字 | 最小、自然支持字号和系统 TTS | OCR 错字不可核对，复杂排版/插图丢失，原页高亮失去依据 | 后续对通过质量验证的文字书提供省空间模式 |
| 只存图片 | 原貌完整，捕获后即可看 | 断网后第一次朗读还要 OCR；识别结果、耗时和语言问题不可预知 | 允许作为中间状态，不作为朗读就绪标准 |
| 原页图片 + OCR + 词框 | 保留版式、可核对文字、可直接朗读与定位 | 图片占空间，需要分片和压缩 | **首版推荐** |
| 文字 + 必要插图/复杂页图片 | 有机会显著减小长期存储 | 需要可靠版面分类、内容保全和切换映射 | 第二轮优化，不能在 OCR 未验证时丢原页 |

若某类页面经当前公开可见阅读表面能直接取得正确正文与定位，优先用正文，减少 OCR；现有 Kindle 主链路仍以图像 + 本机 OCR 为基线，不假设已拿到可导出的完整文本。

每页先对足够清晰的源图做识别，再评估持久化压缩。2048px、1400–1600px、JPEG/HEIF/PNG 都只是候选参数，需用小字、彩色插图、公式和高亮截图对比决定，不能统一压成 768px。

保留显示文字、朗读文字与二者的 UTF-16 范围映射。断行连字、页眉页脚、脚注、跨页段落处理必须可追溯；不能静默用 LLM 改写 OCR 文本。

页尾与下一页首可能属于同一句，朗读单元可跨页，但必须保留每个文字范围对应的页面和词框。自动翻页跟随实际朗读到的范围，不跟随预读或 OCR 队列。

## 5. 整书采集：先验证驱动，再决定扩展范围

### 5.1 三条路径

| 路径 | 用途 | 放行条件 |
|---|---|---|
| A：Page Flip 页序/预览 | 优先探索，可能减小对主阅读位置的干扰 | 当前 iOS WKWebView 确实提供；可枚举正确顺序；有足够清晰页面；源位置可对应；正文和远端进度副作用均验证 |
| B：当前阅读器顺序采集 | 历史实现可参考，可能是实际落地主线 | 复用最新单次语义翻页；稳定确认当前真实页；有起止/覆盖证据；明确处理 Amazon 进度副作用 |
| C：阅读时保存已确认页 | A/B 不可用时的部分能力；也可复用已有确认页加速 | 用户开启保存；只提交已验证内容，展示离散范围和连续可用区间 |

Page Flip 是候选驱动，不再作为整个产品唯一技术前提。A 不成立时评估 B；A/B 都不能达到整书标准时，阶段结论必须是“整书能力未完成”，不能用 C 替代目标。

第一版只选择通过证据门槛的一条整书驱动实现，避免同时维护两套不成熟采集器。驱动的输出契约保持一致，以后可增补另一条。

### 5.2 第一阶段探针要回答的问题

- Web Reader 是否存在可操作的 Page Flip，而不只是原生 Kindle App 存在？
- 页码是否属于当前固定版式？虚拟列表节点重用是否会造成假连续或串页？
- 能否取得总量、明确起点与终点？如果只能观察首尾和逐次翻页，证据能否形成完整遍历链？
- 图像是缩略图还是可阅读页面？小字号 OCR 和肉眼可读性是否通过？
- 原页、源位置、正文指纹和预览 ordinal 能否一一对应？
- 页面总数、内容和版式在一次任务中是否稳定？改变字体/横竖屏后如何失效重建？
- 中途停止、重新开书、WebContent 进程被回收后，能否重新确认最后提交页？
- 采集前后、重新开书后、另一台设备看到的当前位置/最远已读状态是否变化？

最小实验矩阵：至少 6 本合法可访问测试书，覆盖普通小说、长书、插图/固定版式、重复/空白页及不支持 Web/Page Flip 的情况；涉及目标站点和中英文；每条拟发布驱动至少三次完整运行及一次中断恢复。使用自有或可人工核对的测试正文检查首尾和章节边界，不能只看自增页号。

输出按书、站点、版式、系统版本和驱动版本记录能力表。此次计划不执行翻页采集实验。

### 5.3 可靠逐页采集协议

1. 保存用户的在线导航位置、最后实际朗读位置、当前模式和版式；另建下载游标。
2. 获取当前真实可见页面，确认稳定并记录源位置、内容摘要、截图尺寸和版式 generation。
3. 本页资源原子落盘并登记已捕获，OCR 独立排队。
4. 发起一次语义 Next，分配导航 requestID，按 Kindle 自身书籍分页方向执行。
5. 等待该动作的确认与稳定可见页；拒绝单靠 Blob URL、预加载事件、整数百分比或本地自增页号判定成功。
6. 先确认相邻关系，再登记下一页。超时状态是“不确定”，应观察、重定位或暂停，不能直接再次 Next。
7. 使用明确书首/书末语义与页面就绪状态确认终点；一次按钮消失、空图、空 OCR、网络失败和 99% 都不是书末。
8. 逐页校验覆盖、修复缺口、恢复用户导航位置，再独立报告恢复结果和离线包完整度。

相邻页内容完全相同的情况需保留：资源摘要可共享同一图片文件，但两次页出现是两个独立记录。像素没有变化时，只有其他可靠页身份/导航证据足以确认前进才能继续；不能去重删除重复空白页，也不能猜测已经翻页。

### 5.4 “当前进度优先”的具体实施

- 有稳定绝对位置和 Page Flip ordinal 时：先当前页及后续连续窗口，再当前到书尾，再补书首到当前之前。各区间按源锚点合并。
- 只有可靠顺序采集时：先保存当前已确认页。若可以重定位并证明前后区间拼接，采用上述顺序；否则完整任务从已验证书首开始，当前页暂作为独立部分内容，不按猜测插入全书。
- 用户在本地已保存页面阅读时，下载游标与阅读游标各自推进。第一版若不能稳定托管采集 WebView，就先暂停采集再进入阅读，保留断点。
- 已完成的一页立即持久化，不等待全书 OCR。OCR 故障重试只更新原页记录，不能追加到书尾。

### 5.5 不污染进度的要求

CastReader 自己可以做到：所有采集动作标记为 `capture`，不写入用户的“最近阅读”“最近收听”、实际播放时长、听完状态或提醒逻辑。预加载同理。

Amazon 的副作用必须实测。独立 WKWebView、相同 Cookie 下的第二个窗口、停止 CastReader 的进度上报，均不能自动隔离 Amazon Whispersync。

如果 B 路径实测推进 Amazon 最远已读点，第一版不能把它当作无感兜底。应优先修正为不推进的位置浏览路径；若只能保留有副作用的“集中保存”模式，则需作为明确的产品取舍单独评审，界面如实说明，不能宣称“不改变阅读进度”。这是待验证的技术/产品问题，本轮无需因此停下规划。

## 6. 本地存储与真正的断点恢复

### 6.1 推荐数据分层

| 层 | 关键内容 |
|---|---|
| 书籍身份 | CastReader canonical account、产品区域、Kindle 绑定身份/绑定代次、storefront、ASIN 或稳定文档 ID、内容版本 |
| 版式 generation | 捕获版式参数、方向、视口、语言/排版、renderer/capture 版本；同一本书不同版式不混页 |
| manifest | schema、保存目标范围、已确认覆盖区间、缺口、总量来源、起止证据、目录、各类就绪状态、占用 |
| 页面记录 | occurrenceID、源 ordinal/位置、相邻证据、图片摘要和路径、尺寸、OCR 状态/版本、文字/词框分片、质量状态 |
| 下载 journal | taskID、generation、目标范围、最后确认游标、在途导航、未完成 OCR、失败页、暂停原因、原阅读位置及恢复状态 |
| 用户进度 | 最后看见的页、最后实际朗读句/词、语义上下文摘要、用户选择时间、会话 ID；不复用下载游标 |

页面内部可用整数索引渲染，但持久化使用稳定 occurrenceID 和语义锚点。不能把“当前加载窗口的第 3 段”保存成全书第 3 段。分片切换/重排后映射到现有 VM 的临时索引。

### 6.2 文件和内存

建议 `Application Support` 下按账号、绑定和书籍分目录，排除系统备份。用户主动保存的书不放进可被系统随意清掉的临时缓存目录。

用 SQLite 事务索引（可复用项目已选存储方案）和按页资源文件，避免每完成一页重写整个全书 JSON。资源先临时写入并校验，再原子移动，最后提交索引；重启扫描孤儿资源与未完成事务。

- 捕获单线程导航，图片队列初始上限 2–4 页；OCR 初始并发 1，真机测后再增加。
- 阅读只加载当前页及前后邻页；图片按屏幕大小解码，解码缓存有字节上限。
- 校验全书时逐页/分片流式读取，不能把全部图片和全文一次性装进 `ReadingDocument`。
- 把图片原始坐标系、裁剪/旋转变换保存下来，OCR 与压缩后图片使用同一归一化坐标映射。
- 高亮和文字索引可按页延迟加载；目录和覆盖索引独立读取。

### 6.3 断点与更新

- 图片落盘、OCR 完成、页面可朗读是三个提交点，分别恢复；后台时间不足时至少提交现有图片和 journal。
- App 强杀后先验证账号、绑定、书籍和版式，再重新定位最后确认页；找到匹配才处理首个缺口。
- 在途翻页未确认时，不递增 durable 游标；回来后重新核对当前页面，避免重复翻两页。
- 原版式不可恢复时保留旧包，创建新 generation；不混入新字号页面。
- 每页可用即发布该页；“完整书籍 generation”的切换单独原子执行。下载完整状态与“成功恢复在线原位置”分别记录，恢复失败不能把已完成内容丢掉。
- 更新期间旧 generation 继续可读。删除使用失效代次使在途 OCR/写入不能复活已删除内容。
- 若旧 v2 页组包实际只存在开发设备，先统计再决定迁移；存在需要保留的包时提供只读兼容或增量迁移，不能把 schema 较旧直接标成损坏。

### 6.4 存储策略

旧的 20 本/2GB 静默 LRU 应只作为开发原型规则。正式显式保存的书默认保留，只有用户删除或明确的账号解绑清理才释放；LRU 用于临时图片解码、临时预读和可重建数据。

容量面板分列完整书、未完成任务和临时数据。空间不足先停新采集，保留旧完整书和已完成分片，提供逐书清理。

估算模型：`已保存资源 + 剩余页数 × 采样页平均资源大小 + 索引/OCR + 临时空间预算`。同时考虑新旧 generation 共存、在途源图和安全余量。

例如假设图片平均 0.2MB，300 页约 60MB；平均 1MB 则约 300MB，另加 OCR 和索引。这只是计算示例，本轮没有测出实际包体积；前几页样本还要避免封面造成偏差。

## 7. 系统 TTS：优先直接播放

### 7.1 推荐实现与理由

新增轻量 `SystemSpeechPlaybackService`，持有一个长期存活的 `AVSpeechSynthesizer`，通过 `speak()` 直接播放自然句，使用 delegate 范围回调驱动高亮。Apple 提供朗读文本范围回调，但具体声音的粒度和行为仍需真机验证。[Apple 范围回调](https://developer.apple.com/documentation/avfaudio/avspeechsynthesizerdelegate/speechsynthesizer(_:willspeakrangeofspeechstring:utterance:))

相较旧原型的 `write → WAV → Data → AVPlayer`，直接播放省掉合成文件、重复缓存和用音频时长反推高亮的环节，符合本轮的轻量系统 TTS 目标。

保留当前句及后面约两句的有限队列，朗读期间加载下一页文字。分句器需要给异常长句设置可定位的上限切分，不能把整章作为一个 utterance。

### 7.2 高亮、恢复与控制契约

- 每个 utterance 对应实际送入系统的文字以及 `utterance UTF-16 range → source page/paragraph/word ranges` 映射。
- 朗读文本与 OCR 原文一致时直接映射；做规范化时通过明确的映射表返回原词框。不能重新按“第几个字符”硬对齐。
- 中文、英文缩写、数字、emoji、连字、跨页句和混合语言需要独立验证。回调覆盖多个字/词时高亮实际范围，不能伪造更细粒度。
- 所有回调校验 runID、utteranceID、账号/书籍 generation、当前播放器所有者。跳转、切模式、睡眠到期后旧回调不更新 UI 或自动播放。
- 对拟支持的语言/音色要求同步高亮可用；无范围或范围不可靠的音色不标“同步朗读可用”。有可靠句子边界时可显式提供句级高亮，不能默默替代词级承诺。
- 实际播放时长用于收听统计；合成、排队、下载、OCR 时间不扣朗读额度、不算听完。

| 操作 | 首版语义 |
|---|---|
| 播放/暂停 | 使用系统播放、暂停、继续；系统暂停失败时保存确认句锚点后停止 |
| 上一句/下一句 | 精确定位自然句，刷新 runID 和有限队列 |
| 上一页/下一页 | 移动阅读位置；正在朗读时按现有用户翻页语义决定恢复 |
| 改速度/声音 | 从当前确认句边界重启，允许短重复，不漏句；速度映射按系统范围校准，不能假设 `rate × 2` 就是准确两倍 |
| 退出/切模式/睡眠到期 | 统一停止并撤销旧队列，迟到回调不可复播 |
| 强杀后恢复 | 从最近确认句首恢复；明确可重复一句，不能假装恢复到精确毫秒 |
| 时间轴/±15 秒 | 直接 TTS 不提供可靠整书音频时间轴；离线改为句子/页导航，锁屏不提供假的秒级拖动 |

屏幕上显示阅读页或章节进度；“剩余朗读时间”如提供，须标估算。

### 7.3 与现有播放器整合

不让系统 TTS 和 `AudioPlayerService` 同时占有音频输出。通过当前 `PlayerCoordinator` 增加按能力区分的播放适配层，统一 play/pause/stop、状态、Now Playing、耳机命令和音频会话；在线云音频仍用原路径。

“秒级 seek”“句子 seek”“词范围事件”是能力差异，不能强行给系统 TTS 填一组假的 `AudioSegment.timestamps`。也不需要为本轮重写所有在线 ViewModel。

接入最新 `PlaybackSleepTimer` 与到期禁止自动恢复的机制。来电、Siri、音频路由变化、耳机拔出、锁屏恢复依当前所有权统一处理；后台播放需真机长时验收。

### 7.4 声音准备

Apple 的 `speechVoices()` 用于取得本机可用声音；增强声音可能需要用户提前下载，且可能达到 100MB 以上，属于设备共享语音资源而非每书资源。[可用声音 API](https://developer.apple.com/documentation/avfaudio/avspeechsynthesisvoice/speechVoices())、[Apple 下载语音说明](https://support.apple.com/en-gb/111798)

按准确语言/地区优先选择已验证声音，试听成功后固定 voiceID。不能仅凭能创建 `AVSpeechSynthesisVoice` 就保证飞行模式可合成；也不应每次自动选更高 quality 而忽略语言匹配与实际可用性。

首次保存时检查并允许试听，飞行模式冷启动测试覆盖默认和已下载声音。监听可用声音变化；声音被删除时可使用同语言已验证替代，明确通知声音变化。没有合适声音时仍可看书和本机 OCR，不偷偷切云端。

### 7.5 备选技术事实

Apple 还有 `write(_:toBufferCallback:toMarkerCallback:)`，提供音频和 marker metadata；当前本机 iPhoneOS 26.5 SDK 头文件标为 iOS 16+，覆盖项目 17.6 的部署下限。[Apple write + marker API](https://developer.apple.com/documentation/avfaudio/avspeechsynthesizer/write(_:toBufferCallback:toMarkerCallback:))

若后续确实需要有精确时轴的系统音频片段，可独立验证此路和 `byteSampleOffset` 的实际语义、跨 buffer 行为、音色支持情况。它不证明旧原型按 delegate 时刻取已写帧数的方法正确，也不构成本轮增加音频文件缓存的理由。

## 8. 进度、账号与离线 Pro

### 8.1 进度分开、内容身份统一

同一本书的在线/离线入口共享 canonical 内容身份，但保留不同 generation 的位置映射。至少区分下载游标、手动阅读位置、实际收听位置和 Amazon 源位置。

复用发布版 `ReadingResumeCheckpoint`、`KindleNavigationPosition`、`KindleListeningAnchor` 以及重排上下文定位思路。内容窗口 index、百分比、短期 Blob URL 都不能成为唯一恢复依据。

联网返回在线时，优先按源位置 + 文字上下文解析；精确匹配失败就停留在可确认页并提示，不根据近似百分比跳转后自动朗读。Amazon 同步弹窗保留用户选择权。

未来接入统一进度服务时按其 base revision/session 冲突契约合并；这次先把本机 checkpoint 和离线分支存好。不能把“最后收到的离线包”覆盖成云端最新进度，也不能简单取最大百分比阻止用户主动回读。

### 8.2 账号边界

- 本地包按 CastReader canonical 账号和 Kindle 绑定边界隔离，不能只用 ASIN。区域切换也不能误命中另一账号/绑定的数据。
- Kindle 稳定身份不可得时，以当前明确绑定产生的代次隔离；重新绑定默认新代次，不拿会旋转的 Cookie hash 充当永久用户身份。
- 短暂断网、session 刷新失败不等于主动登出；保留已认证的本地账号身份和已授权包，使冷启动入口可达。
- 显式换账号立即停止播放/采集并隔离旧资源；解绑 Kindle 清理对应绑定包与任务，删除操作不能误删新绑定数据。
- 本轮只规划用户主动保存到 App 私有空间。书籍图片/OCR 不上传 CastReader 服务端，不增加文件导出或分享。技术可访问和持久化使用边界是不同问题，整书发布前需对实际来源的使用条件完成核对；不把历史“禁止整书导出”的描述误读为本轮不得讨论本机保存。

### 8.3 Pro 必须真的能断网使用

离线包准备、更新、打开阅读与朗读均沿用 Pro 定位；到期保留内容和位置，允许管理/删除，恢复权益后立即复用。离线系统 TTS 不额外消耗云端 TTS 配额。

统一通过账号权益解析层判定：已有 StoreKit 本地可验证交易可作为离线路径之一；Web/Stripe、Android/中国区等 server Pro 需要可离线验证的服务端签名凭据，不能要求每次联网查 `/api/pro/status`，也不能持久化一个裸 `isPro=true`。

建议离线凭据包含 canonical account、设备/安装绑定、功能范围、签发/到期时间、权益有效期、版本和 key ID，在线时自动刷新并处理已知撤销。最长离线窗口建议评审为 30 天（且不超过真实权益到期时间），比旧讨论的 7 天更适合旅行；这是新产品建议，尚未修改后端或订阅规则。

首次准备时告知“离线可用至某日”，测试断网重启、跨午夜、修改设备时间、凭据过期及退款后再联网。可信时间采用最近服务器时间与本地保守校验；完全离线时无法实时获知退款，不承诺即时撤销。

内容就绪状态和权益有效状态独立。查询失败不把已保存状态抹掉，权益到期不删包，缺凭据显示具体原因；不要把所有失败统称“请重新下载”。

## 9. iOS 前后台限制

普通 App 进入后台通常会被挂起，额外后台时间用于保存关键状态，不能视为可以无限驱动网页翻页。[Apple 后台执行模式](https://developer.apple.com/documentation/xcode/configuring-background-execution-modes)、[完成关键后台工作](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time)

基础版本承诺：前台准备内容；后台/锁屏保存断点并暂停网页采集；已经保存的内容可继续系统朗读。

iOS 26+ 的 `BGContinuedProcessingTask` 为用户发起的长任务提供新能力，可作为以后 OCR/校验工作的优化候选；它不能直接推出认证 WKWebView 的 WebContent 渲染在后台同样可靠，也不覆盖 17.6 的基础支持。[Apple 长任务说明](https://developer.apple.com/documentation/backgroundtasks/performing-long-running-tasks-on-ios-and-ipados)

不使用静音音频维持采集，不把短期 Blob URL 交给 `URLSession` 后台下载并假定可长期恢复，不把“后台朗读支持”写成“后台整书下载支持”。

## 12. 验收：以真正断网和真实书为准

### 12.1 内容完整性

区分两种覆盖证明：

- `declaredIndex`：由源端给出完整当前版式页索引，捕获的 occurrence 覆盖其全部预期项，每项图像和定位已验证。
- `verifiedTraversal`：没有可靠总页数时，从已确认起点逐次单页前进至已确认终点，整条相邻关系链连续且无未决跳转。该证明方式需单独真书验收，不能用自增序号替代。

任一方式都必须覆盖用户选择的范围、同一内容版本/版式、无缺口、资源摘要有效；总页数未知不代表可以凭采集结束猜测完整。章节、前后附文和固定版式资源也纳入所声明范围。

“整本可朗读”还需所有含可读文字页面 OCR 达标，以及本机语言声音可用。明确空白页/纯插图页可没有 OCR 文本，但必须有图片与分类证据；OCR 空返回不能直接归为空白。

### 12.3 量化指标

建议先作为目标线，P0 用最低支持设备建立基线；这些不是本轮实测结果。

- 缺页/乱序/错账号读取、采集覆盖实际阅读进度：0 容忍。
- 已保存书冷启动打开 P95 ≤ 2 秒；已准备音色首次出声 P95 ≤ 1 秒，后续热启动 ≤ 500ms。
- 范围回调到高亮呈现 P95 ≤ 100ms；另用屏录+音频人工检查感知同步，不能只测 UI 回调延迟。
- 停止/睡眠到期后目标 250ms 内停止可闻语音，且后续回调不能复播。
- 1000 页与 100 页在相同阅读窗口下，资源内存基本恒定；绝对上限在最低支持真机上测定。连续 60 分钟内存无持续增长。
- 冷启动不扫描/解码整本；单页损坏修复不重下整本。
- 严格断网测试中内容读取、OCR 和 TTS 无网络依赖；联网选择本机语音时也不能回退云 TTS。账号/分析上报独立排队，不阻塞阅读，不携带正文或页面。
- 记录每页捕获/OCR/落盘耗时、首个连续可用区间耗时、全书耗时、暂停恢复成功率、按原因失败率、图片/OCR占用；日志不记录正文、图片、Cookie 或可重放资源 URL。

## 13. 本轮最终决策与未验证项

可以直接按此进入后续实现规划的决定：系统 TTS 直接播放；原页/OCR 双层保存；显式保存不做静默 LRU；下载/阅读/收听游标分开；分片持久化；完整度与可朗读状态分开；从最新发布基线增量接入。

必须通过实验再确定的事项：选用 Page Flip 还是顺序采集、Amazon 进度影响、全书覆盖证明是否成立、各语言声音的范围同步质量、压缩参数和实际耗时。Pro 离线凭据最长 30 天为产品建议，后端协议需按现有 canonical 权益体系落实。

目标完成的定义是：用户明确保存本书后，在声明支持的书型和保存范围内，飞行模式重启仍能从自己的进度连续看和听；已保存内容可解释、可恢复、可管理，且不能以一个局部页面组冒充整本书。

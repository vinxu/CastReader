# 邮箱验证码登录（email-OTP）— 后端接入清单

**状态**：iOS / Android 客户端已实现并发布就绪；**后端未启用**，两端当前显示「邮箱登录暂未开放」。
后端把插件开起来后，**客户端无需发版自动点亮**。

**日期**：2026-08-13
**发起背景**：见文末「为什么要做」——这不只是多一个登录方式。

---

## 一、为什么要做（两个真实问题）

**1. 硬登录墙下的单点故障。** App 已改为首启硬登录（全员生效），登录挂 = 所有人打不开。
当前只有 Google + Apple 两条通道，而在 Google 服务不可达的网络下**实际退化成 Apple 单通道**。
邮箱验证码只依赖自家后端，是唯一不依赖第三方授权服务的冗余通道。

**2. Apple 隐藏邮箱用户跨不到 Web/扩展。**
用户在 iOS 用 Apple 登录并选择「隐藏我的邮箱」，账号 email 是
`xxxxxxxx@privaterelay.appleid.com`。而 Web / Chrome 扩展只有 Google 登录，
拿到的是真实 Gmail —— **后端是两个 user，iOS 上买的 Pro 在扩展里看不到**。

relay 邮箱**可以收信**（Apple 转发到用户真实邮箱），所以 Web 端支持 email-OTP 后，
用户输入 relay 地址即可登进 iOS 那个同一账号。这是不动 Apple provider 配置的最短解法。

> 长期正解仍是给 Web 端补 Sign in with Apple（Services ID 关联同一 primary App ID，
> 可拿到与 iOS 完全相同的 `sub` 与 relay 邮箱），本次先不做。

## 二、端点契约（客户端已按此实现，请勿改动形状）

### 1. 发送验证码

```
POST /api/auth/email-otp/send-verification-otp
Content-Type: application/json

{ "email": "user@example.com", "type": "sign-in" }
```

### 2. 验证码登录

```
POST /api/auth/sign-in/email-otp
Content-Type: application/json

{ "email": "user@example.com", "otp": "123456" }
```

**响应必须包含 `user.id`** —— 客户端拿它作为 `backendUserId`，Pro 按账号查询依赖它：

```jsonc
{
  "token": "...",              // 可选，客户端会存起来备将来换 mobile session
  "user": {
    "id": "usr_xxx",           // 必需
    "email": "user@example.com",
    "name": "...",             // 可选
    "image": "https://..."     // 可选
  }
}
```

以上是 better-auth `emailOTP` 插件的默认路由与响应形状，装上插件即满足。

### 3. HTTP 状态码语义（客户端已硬编码分支）

| 状态码 | 客户端行为 |
|---|---|
| `2xx` | 成功 |
| **`404`** | **判定为「后端未启用此功能」**，提示「邮箱登录暂未开放，请使用 Google 登录」 |
| `400` / `401` / `403` | 提示「验证码错误或已过期」 |
| 其他 | 提示「登录失败，请稍后重试」 |

⚠️ **不要用 404 表达「邮箱不存在」等业务含义** —— 客户端会误判为功能未上线。
业务性拒绝请用 400/401/403。

## 三、实施步骤

### 步骤 1：邮件发送服务

不需要采购，免费额度足够起步。推荐 **Resend**（Vercel 生态，接入最省事）；
SendGrid / Postmark / AWS SES 同理。

验证发信域名（加 SPF / DKIM DNS 记录），建议用子域，例如 `mail.castreader.com`。

### 步骤 2：⚠️ 在 Apple Developer 后台注册发信域名（**不做则方案失效**）

**Certificates, Identifiers & Profiles → Services → Sign in with Apple for Email Communication**

把发信域名与发件地址（如 `noreply@mail.castreader.com`）登记进去。

**不做这一步，Apple 会拒收所有发往 `@privaterelay.appleid.com` 的邮件**，
隐藏邮箱用户永远收不到验证码——而且**失败是静默的**，你在 Resend 后台看到的是投递成功。

这一步正是本方案能解决「Apple 隐藏邮箱跨端」的前提。

### 步骤 3：better-auth 装 emailOTP 插件

```ts
import { betterAuth } from "better-auth";
import { emailOTP } from "better-auth/plugins";
import { Resend } from "resend";

const resend = new Resend(process.env.RESEND_API_KEY);

export const auth = betterAuth({
  // ...既有配置
  plugins: [
    emailOTP({
      otpLength: 6,
      expiresIn: 300,               // 5 分钟，与客户端 60s 重发冷却相容
      async sendVerificationOTP({ email, otp, type }) {
        await resend.emails.send({
          from: "CastReader <noreply@mail.castreader.com>",
          to: email,
          subject: `${otp} — CastReader 登录验证码`,
          text: `你的 CastReader 登录验证码是 ${otp}，5 分钟内有效。\n\n如果不是你本人操作，请忽略本邮件。`,
        });
      },
    }),
  ],
});
```

### 步骤 4（建议）：邮件文案跟随语言

CastReader 是九语产品（en / zh / ja / es / fr / de / pt-BR / it / hi）。
验证码邮件建议按用户语言发。当前客户端**未传语言字段**——若要做，
请先与客户端约定新增字段（例如 `locale`），不要擅自改已有请求形状。

不做也不阻塞上线，默认英文即可。

## 四、验收

后端部署后，用这两条命令确认（无需客户端）：

```bash
curl -i -X POST https://castreader.ai/api/auth/email-otp/send-verification-otp \
  -H 'Content-Type: application/json' \
  -d '{"email":"你的邮箱@example.com","type":"sign-in"}'
```

期望 `2xx` 且真实收到邮件。**当前未接入时返回 404。**

```bash
curl -i -X POST https://castreader.ai/api/auth/sign-in/email-otp \
  -H 'Content-Type: application/json' \
  -d '{"email":"你的邮箱@example.com","otp":"收到的验证码"}'
```

期望 `2xx` 且响应体含 `user.id`。

**关键验收项（本方案的立项理由，务必测）**：
用一个 `@privaterelay.appleid.com` 地址走一遍上述流程，确认**真的收到了转发邮件**。
收不到即为步骤 2 未生效。

客户端侧验收：iOS / Android 登录墙 →「使用邮箱验证码登录」→ 收码 → 登录成功进入 App。

## 五、已知限制（不阻塞上线）

**邮箱账号拿不到 `cms_` 会话。** `/api/mobile-auth/session` 目前只接受
`provider = google | apple`（传 `email` 返回 422）。因此邮箱登录的用户：

- 声音克隆等依赖 `cms_` 会话的功能 fail-closed（当前 `voiceCloningEnabled = false`，无影响）
- iOS 的 `verify-apple` / Android 的 `verify-android` 购买上报会跳过，走既有的
  pending-sync 降级（本机 Pro 立即生效，跨端同步待后续）——与中国区手机号账号同一条路

客户端已把 better-auth 返回的 `token` 存进 Keychain / DataStore，
后端若将来支持用它换 `cms_` 会话，可直接补上，无需逼用户重新登录。

## 六、附：另一个待修问题（独立于本方案）

探测发现 `/api/auth/sign-in/social` **未配置 apple provider**：

```
provider=google  →  401 INVALID_TOKEN       （已配置）
provider=apple   →  404 PROVIDER_NOT_FOUND  （未配置）
```

导致 iOS 每个 Apple 登录用户的 `backendUserId` 恒为空，
`AuthService.needsAppleRelink` 对所有 Apple 用户恒为 true —— 设置页那句
「重新登录同步 Pro」的提示，用户重登多少次都消不掉，根因在后端。

Pro 目前未受影响（`/api/mobile-auth/session` 支持 apple，靠 relay 邮箱那条线工作），
但建议单独排期修掉。

# 绑定书库错误处理 · 跨端对齐指南

适用于 **Kindle** 与 **微信读书**。iOS 已实现，Android 按本文落地。

配套：`Kindle登录页自动恢复-跨端对齐指南.md`（取证细节）、`绑定书库阅读器生命周期-跨端对齐指南.md`（销毁契约）、`WeRead-iOS-Login-Session-Contract.md`（微信读书登录铁律）。

## 0. 首要原则：别管它

**阅读器就是一个普通网页。打开、加载、朗读。**

不要给它加加载态遮罩、就绪探测、看门狗、重试阶梯、故障分类。**只有在确实出问题时才介入，而且介入方式只有两种：**

1. **自动刷新书架**（用户无感）
2. **引导用户重新绑定**（唯一允许打扰用户的情况）

> 这一条是踩出来的。iOS 曾经实现过一整套：6 类故障 + 5 种处置 + 静默预算 + 退避阶梯 + 30 秒看门狗 + DOM 就绪轮询 + 三张终态卡片。结果是**它自己制造了自己要解决的问题**——
> - 加了遮罩，才需要知道「什么时候算加载完」，于是要做就绪探测
> - 就绪判据选了 `didFinish`，而 Cloud Reader 是 SPA，实测**响应 1 秒就到、`didFinish` 永远不来**，于是白等 30 秒看门狗，最后弹一张「服务暂时不可用」——**而书其实早就显示在屏幕上了**
>
> 不盖遮罩，这一整串都不存在。**已全部删除。**

## 1. 唯一需要介入的情况

Amazon 把书的深链换成了它的登录页：

```
read.amazon.com/?asin=<ASIN>
   → 302 → www.amazon.com/ap/signin?openid.mode=checkid_setup&...
```

判定：**导航响应的落地 URL** 含 `/ap/signin`、`/ap/cvf`、`authportal` 或 `openid.`。

## 2. 处理流程

```
落地 = 登录页
   ↓
盖住页面（用户不该盯着一个陌生的 Amazon 表单）
   ↓
后台加载一次 read.amazon.com/kindle-library
   ├─ 成功 → 重新加载原书 URL → 正常进书（实测全程 3~6 秒）
   └─ 仍是登录页 → 撤遮罩 + 原生卡片引导重新绑定
```

**每次阅读会话只自动修一次**，成功进书后重置。账号真的退出时不能自旋。

### 关键：判定要挂在「响应」上，不是「加载完成」

iOS 实测：登录页的 HTTP 响应 **1 秒**就到，而 `didFinish` **一次都没触发过**。把判定挂在加载完成事件上，等于永远不会触发。

- iOS：`decidePolicyFor navigationResponse`
- Android：`onReceivedHttpError` / `shouldInterceptRequest` / `doUpdateVisitedHistory`，或在 `onPageStarted` 判 URL

### 书架那一跳的约束

- **必须用书架客户端配置**：不带桌面阅读器 UA、不注入阅读器脚本。带桌面 UA 请求书架，Amazon 不会刷新 book session。
- **不要扫描书架、不要触发同步**。页面加载完成本身就是全部机制。
- iOS 上这一跳实测 2 秒。

## 3. 重新绑定引导

不要把 Amazon 的原始登录页丢给用户就不管——他不知道这跟「Kindle 绑定」有什么关系。展示原生卡片：

> **Kindle 登录已失效**
> 需要重新绑定 Amazon 账号才能继续。重新绑定并同步后，书架和听书进度都会回来。
> 〔重新绑定 Kindle〕〔返回〕

点击后：清 Amazon 网站数据 → 清书架缓存、`hasConnected = false` → **保留听书进度锚点**（按 book id 存，重新同步后自动对上；这次失效不是用户主动解绑，不该让他丢阅读位置）→ 关闭阅读页 → 打开绑定流程。

**解绑不要做成全自动。** 它会清空书架，而落地判定是启发式的，误判一次就把用户书架清了。一次点击确认，引导同样明确。

## 4. 其他失败一律不要发明机制

| 情况 | 做什么 |
|---|---|
| 断网 / 超时 | **只记日志**，交给 WebView 自己（跟浏览器一样）。**绝不能引向重新绑定**——为一段地铁隧道清掉用户书架是最糟的误判 |
| 4xx / 5xx / 429 | 只记状态码。没有观测到需要处理，就不要预先造处置 |
| 加载慢 | 不是故障。不要设超时把它判成错误 |
| 书籍失效弹窗（`open this book from the library again`）| 既有的书架重扫恢复，与本文无关，别混在一起 |

## 5. 微信读书：同样原则，逻辑独立

只共用「别管它 / 出问题才引导」这个原则，**判别与处置完全分开写**：

- 微信读书没有 OpenID 网关，登录态是 Vue 登录弹窗，不是 URL 跳转
- 它的二维码登录会话**经不起任何重新导航**（见登录合同）
- 因此**不得照搬 Kindle 的自动刷书架**

微信读书侧只做一件通用的事：**传输层失败时的有界重试**，且必须满足「入口恢复状态机处于 idle」——导航压根没成功，没有活的登录会话需要保护。其余全部交回它自己的入口恢复状态机。

> iOS 修复前的真实缺陷：所有失败（含纯超时）都被送进入口恢复，等于断网时把用户推去扫书架和登录。

## 6. 诊断埋点

cookie 值**一律不得入日志**。iOS 只记「名称 + 有效期 + 值的 8 位单向摘要」——足以看出 token 是否轮换或消失，不足以还原凭据。另记：落地分类、重定向逐跳、主 frame 状态码、距上次成功进书/加载书架的分钟数、进程启动横幅。

这些是排查的全部依据，但**它们只是观测，不要让观测反过来驱动产品行为**。

## 7. 验收标准

1. 正常开书：**不增加任何网络请求，不加任何遮罩**，表现和浏览器一致。
2. 落到登录页：用户全程看不到 Amazon 表单，3~6 秒后自动进书。
3. 真退出登录：只自动修一次，随后出「需要重新绑定」卡片，**听书进度不丢**。
4. 飞行模式：**不出现任何与账号/绑定相关的提示**，绑定数据零变化。
5. 加载慢：只是慢，不会被判成错误。
6. 日志能回答：有没有落到登录页、刷书架成没成、修了第几次。

# CastReader iOS 使用数据分析（2026-08-03）

## 结论摘要

当前数据已经能看清方向，但还不能直接拿来做“真实用户规模、整书完成率、付费转化率”的经营判断。

最明确的产品信号有三个：

1. 朗读的首音链路健康，`read_start → read_first_audio` 为 98.6%，首音 P50 294ms、P95 1.10s；当前主要矛盾不在 TTS 首音。
2. 解读链路明显偏弱：78 次开始只有 51 次进入首块播放（65.4%），37 次首块达到 80%（47.4%），26 次进入第二块（33.3%），最终完整完成 13 次（16.7%）。首块 P50 约 7.7–9.7 秒，P90 约 14–15 秒。
3. Kindle 用户数不算大，但使用深度非常高，是最值得验证的高价值人群；同时 Kindle 自动翻页把一次连续阅读切成大量 `read_start/read_end`，导致当前“阅读会话数、完成率、3/5/10 分钟到达率”失真。

因此建议先修分析口径，再把下一轮产品资源集中在“解读首块提速 + 首次价值激活 + Kindle 连续阅读”三件事上。

## 数据范围

- 数据源：生产 PostgreSQL `analytics_events`，只读查询。
- 筛选：`client_platform=ios`、`environment=production`、有 canonical `event_name`。
- 客户端发生时间：2026-07-15 08:53 至 2026-08-03 18:05（北京时间）。
- 事件：14,960 条。
- 匿名设备：155 个。
- App 会话：401 个。
- 带后端登录用户 ID：11 个（约 7.1%）。
- 日活：完整日约 7–18，均值约 12。
- 75/155（48.4%）设备出现至少 2 个 App 会话。

这里的“设备”不是商店下载用户。匿名 ID 会受重装影响，而且 Release/TestFlight 都会被标记为 `production + app_store`，所以样本可能混有测试人员与预发布用户。

## 数据链路质量

事件传输本身表现良好：

- 缺失 `event_id`：0。
- 重复 `event_id`：0。
- P95 上报延迟：3.9 秒。
- 36 条延迟超过 5 分钟，其中 34 条超过 1 小时，说明持久队列重放有效；平均值 410 秒被少数长延迟事件拉高，不能代表常态。

不过分析语义存在四个 P0 问题：

1. 首页 Pro 卡片曝光被记成 `paywall_shown`。232 次所谓付费墙中，154 次（66.4%）只是首页卡片曝光，不是真正打开付费墙。
2. Kindle 自动翻页会结束当前 analytics read session，原因是 `kindle_page_handoff`，下一页重新开始一个 read session。3,462 个 `read_end` 中有 1,161 个（33.5%）是这种页间交接。
3. `client_variant` 固定为 `app_store`，无法区分正式商店、TestFlight、内部 Release 包；10/12 的购买成功结果因此不能视为真实收入转化。
4. 后端代码注释称 8 月 1 日前移动端漏斗数据为 0，但生产事实在 7 月 15 日起已有完整 canonical 事件，且绝大多数接收延迟仅数秒。该修复说明与当前 normalize/legacy allowlist 逻辑及事实不一致，需要单独复核，避免错误地废弃历史数据。

## 用户与激活

- 155 个观察设备中：
  - 106 个产生内容意图（68.4%）；
  - 90 个成功进入内容就绪（58.1%）；
  - 81 个开始朗读（52.3%）；
  - 40 个尝试解读（25.8%）；
  - 70 个没有开始朗读或解读（45.2%）。
- 内容会话口径：529 次意图、301 次 ready、3 次明确失败、225 次既无 ready 也无 failed。
- ready 后的模式分布恰好是 243 次朗读、58 次解读，说明真正进入 Reader 后开始核心功能的意愿不错；主要流失发生在“打开 App/选择入口 → 内容就绪”之前。

“225 次 orphan intent”不能直接判定解析失败。文件入口先记 `file/unknown`，成功后才知道 PDF/EPUB/DOCX；用户取消 picker、URL/文本未提交也不会记失败。下一版应拆出 `source_opened / input_confirmed / cancelled / processing_started / ready / failed`，否则无法区分 UX 流失与技术失败。

按首次被埋点观察到的设备粗算，D1 App 打开留存约 19%，D7 约 7%。这不是正式留存：窗口首日包含老用户，且成功条件只是打开 App，不是完成有效阅读。

## 内容来源

按内容意图：

- Kindle：124 次，26 个用户；85 次 ready，25 个用户。
- 文件：118 次，46 个用户；意图阶段格式为 unknown，成功后分别落到 EPUB 26、PDF 19、DOCX 4、文本 2 等。
- URL：48 次，27 个用户；17 次 ready。
- 剪贴板：文本 28/28 ready，网页 26/26 ready，是当前最稳定的轻入口。
- 相机：17 次意图、5 次 ready。
- 相册：11 次意图、2 次 ready。

相机/相册和 URL 的 ready 比例低，但由于取消和失败没有闭环埋点，现阶段应先补诊断，不宜直接断言 OCR 或解析质量差。

Kindle 的特点是“用户少但极深”：仅一个设备在同一音色配置下就产生了 529 次 Kindle `read_start`，占全部 3,582 次 read start 的至少 14.8%。这可能是重度用户，也可能是测试设备；需要先区分分发渠道，再决定是否把 Kindle 作为主增长楔子。

## 朗读

- `read_start`：3,582。
- 有首音：3,533，98.6%。
- 无首音：49，1.4%。
- 有 `read_end`：3,461，96.6%。
- 缺 `read_end`：121，3.4%。
- 首音延迟：P50 294ms、P90 812ms、P95 1.10s；最大 24.7s。
- 明确 `tts_failed` 约 29 次，占已有结束事件不足 1%。

表面上的单 read session P50 播放时长只有 38 秒、仅 60 次达到 3 分钟，但这是 Kindle 页面切分造成的口径问题，不能解释为用户只听 38 秒。应在自动翻页时继承同一个 `read_session_id` 和累计播放时间，页面级交接另记诊断事件。

## 解读

漏斗：

- 开始：78。
- 首块实际播放：51（65.4%）。
- 首块播放达到 80%：37（47.4%）。
- 第二块开始：26（33.3%）。
- 全部完成：13（16.7%）。
- 额度阻断：8（10.3%）。
- 明确系统失败：1 次 `block_prepare/http_400`。

首块等待：

- General：P50 9.7s、P90 14.2s（n=29）。
- Book：P50 7.7s、P90 15.2s（n=18）。
- Paper：P50 8.7s、P90 11.9s（n=4）。
- Study：样本仅 2 次，均值约 15.5s。

解读的问题更像“等待与价值兑现太晚”，不是大量技术报错。建议目标设为首个可听内容 P50 < 5s、P90 < 8s：先流式产出第一句讲解并播放，标注计划和后续块并行生成；等待态明确展示当前阶段与预计价值；保留用户中途退出后可恢复的结果。

## 付费

- `paywall_shown` 232 次中，154 次只是首页 Pro 卡片曝光。
- 真实权益触发相关事件：Pro 音色 35、朗读额度 31、首页次级入口 7、解读额度 5。
- 购买开始 12 次；结果 10 成功、2 取消；权益激活事件 8 次。

这个成功率异常高，且客户端无法区分 TestFlight/Sandbox，不能当作真实商业转化。需要用 App Store Server API/交易事实对账，并在匿名产品事件中增加受控的 `distribution_channel` 与 `transaction_environment`，不记录交易敏感信息。

## 建议迭代顺序

### P0：先让数据可决策

1. 首页卡曝光改发独立 `home_pro_card_impression`，只有真正展示付费页才发 `paywall_shown`。
2. Kindle/微信读书等自动翻页继承 read session；增加页面交接诊断事件，但不重开价值会话。
3. 增加正式 App Store / TestFlight / 内部包区分；购买结果与服务端交易事实对账。
4. 内容导入补齐确认、取消、处理、成功、失败阶段；将用户取消从系统失败中分开。
5. 直接产出 `meaningful_read_reached` 或可靠的会话级 rollup，按指标字典计算 WMRU、D1/D7 有效留存。
6. 后端事件白名单从 JSON 合同生成，并监控 accepted/rejected 比例，禁止“HTTP 200 但核心事件被拒绝”静默发生。

### P1：产品价值

1. 解读首块提速与渐进式播放，优先解决 7–15 秒等待和首块掉失。
2. 首次使用引导围绕“一分钟内听到第一段”设计，优先突出成功率最高的剪贴板/粘贴入口；不要在首次价值前把 Pro 卡片当成主要视觉焦点。
3. Kindle 作为高深度方向继续打磨连续播放、后台稳定性、进度恢复、章节导航；先排除测试设备后再评估其真实留存与付费价值。

### P2：实验

1. 相机/相册 OCR 漏斗补齐后，再决定是优化权限说明、拍摄引导、裁剪，还是识别质量。
2. 在首次有效阅读后测试登录提示，以改善目前仅约 7% 的可跨设备身份覆盖。
3. 按“首次价值后付费墙”设计权益实验，分别观察朗读额度、解读额度、Pro 音色的真实转化。

## 当前数据缺口

本报告覆盖端内产品事件，不包含 App Store Connect 的曝光、产品页浏览、下载、卸载、商店留存与退款，也没有 Crash/MetricKit 权威数据。完整 iOS 经营看板应把 App Store Connect、服务端交易、产品埋点和崩溃质量四类数据按日期/版本并列，而不是只看 `analytics_events`。

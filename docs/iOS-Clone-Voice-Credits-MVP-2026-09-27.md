# iOS 下一版本 P0：克隆音色额度加购 MVP

规划日期：2026-09-27。实现更新：2026-09-28。状态：已实现本地 MVP；155 项模拟器自动化测试及连续购买 UI 验收通过，尚未完成 Apple 在线 Sandbox、完整 Read/Explain 界面续播与部署验收，不是正式交付或已发布版本。

用户已明确：每月基础额度 120 分钟；无论余额是否耗尽都能主动购买更多额度；本功能是 iOS 下一版本最重要的迭代。版本号在确认实际发布基线后确定。

用户已进一步确认：**MVP 先仅开放 Pro 用户加购**，余额为 0 或大于 0 均可购买。沿用现有 Pro 判定（含有效试用）与每个会员月度周期 120 分钟。以下套餐规格、售价、到期后的使用条件和开发估算属于本方案建议，尚未配置到生产。

## 1. 产品规则

| 项目 | MVP 规则 |
|---|---|
| 基础额度 | 每个有效 Pro 会员月度窗口 120 分钟，沿用服务端会员周期；年付会员逐月获得，非一次发放 1,440 分钟 |
| 重置 | 基础额度不结转，显示服务端 `resetAt`；不按手机日期或自然月 1 日重置 |
| 加购商品 | 仅一个商品：克隆音色 120 分钟加量包；一次购买增加 7,200 秒，可反复购买，不自动续费 |
| 候选售价 | 中国区 ¥18 / 包、美区 US$2.99 / 包；已配置到未提交的 App Store Connect 消耗型商品草稿，尚未上线；其他地区使用 StoreKit 本地价格 |
| 购买时机 | 余额为 0、剩余 30 分钟、基础额度全满、已有加购余额时都可买；余额多少不能作为购买条件 |
| 使用顺序 | 先用本周期基础额度，再用加购额度；一次生成可跨两个余额扣减 |
| 加购有效期 | 永久保留，不随基础额度重置或取消续订清零，不转赠、不提现 |
| 会员到期 | 本方案暂沿用“使用克隆需有效 Pro”：加购余额保留，续费后可继续用；购买页必须写清此条件。若改为到期后加购余额独立可用，需同步改变克隆准入，不能只改文案 |
| 计费单位 | 对成功生成、验证通过且可交付的音频按实际时长结算；账本用整数毫秒，页面显示分钟；不对每段向上取整到整分钟 |
| 倍速 | 以服务端生成的音频时长为准；客户端 2x 播放不减半扣额，暂停不重新计费 |
| 免费操作 | 创建、管理声音和固定试听不扣使用额度；这些操作的成本仍要纳入运营核算 |
| 重放与失败 | 已有音频缓存重播、同一请求的成功结果重取不重复扣额；未成功的生成释放预留 |
| 使用范围 | 朗读和解读共享余额，所有允许使用的克隆声音共享；新包不会增加普通音色、创建次数或其他 Pro 权益 |
| 账号归属 | 购买前登录；额度归属于验证后的 canonical 账号，换机/重装登录该账号后可取回剩余余额 |

Apple 的 [App Review Guidelines 3.1.1](https://developer.apple.com/app-store/review/guidelines/#in-app-purchase) 明确购买的 credits 不应过期，因此加购余额必须独立于按周期恢复的会员权益。基础额度的现有合同见[声音克隆统一规范](./声音克隆-跨端权限与技术架构统一规范.md)。

例子：基础剩余 30 分钟，加购 120 分钟后总计 150 分钟；生成 40 分钟后基础为 0、加购为 110；到下一会员月度窗口，基础恢复 120、加购仍为 110，总计 230 分钟。

## 2. 用户流程：一个购买页、两个入口

**常驻入口**：在现有“我的声音”额度卡上增加“购买更多额度”，有额度也始终可见。声音选择界面可复用同一入口，不另造商店。

额度卡示例：

```text
克隆音色额度
本周期剩余       30 / 120 分钟
加购剩余        120 分钟
合计可用        150 分钟
基础额度于 10 月 15 日恢复

[购买更多额度]
```

**耗尽入口**：朗读/解读准备生成下一段而额度不足时，在安全段落边界暂停。展示“购买 120 分钟”“切换普通音色”和恢复日期，保留当前阅读位置，不静默换音色，不继续预取克隆音频。

购买页只展示一个加量包、StoreKit 返回的本地化价格、购买按钮和规则：“一次购买，不自动续费；加购额度不过期；优先使用基础额度；需有效 Pro 才可使用”。价格不能硬编码为页面文案。

支付状态必须区分：购买中、用户取消、等待批准、已付款正在同步额度、已到账、可重试错误。只有服务端确认到账后才显示“已增加 120 分钟”。已付款但未到账时提示正在同步，不能诱导再次付费。

从耗尽页购买成功后提供“继续朗读/解读”；从设置主动购买后留在原页面。恢复沿用原任务和请求标识，不能从头生成已收费内容。

## 4. 最小技术闭环

### 4.1 购买与到账

采用 StoreKit 2 消耗型内购（Consumable），建议商品 ID：`ai.castreader.clone.minutes120`。已创建 App Store Connect 草稿商品 `6816697780`，未提交审核。

```text
登录 + 检查商品与服务可用性
  → 绑定 canonical 账号的 appAccountToken
  → StoreKit 购买
  → 客户端提交签名交易
  → 服务端校验 Apple 签名、环境、Bundle、商品、账号和退款状态
  → 数据库事务内登记唯一交易并增加加购余额
  → 返回最新余额
  → 客户端确认交付后 finish()
```

建议新增额度查询与交易兑换接口，或在现有认证接口上作兼容扩展。商品所对应的毫秒数只能由服务端白名单决定，不能信客户端传入的金额、分钟或 user ID。

数据库最少保留：购买记录（环境、Bundle、transaction ID、账号、商品、发放量、退款状态）、账号加购余额、使用账本及各来源扣额明细。发放以 `(environment, bundleId, transactionId)` 全局唯一；月度基础额按权威会员周期唯一。客户端重试、交易监听和服务端通知进入同一幂等处理器。

只有服务端提交成功才 finish。通过 `Transaction.updates`、启动时的 `Transaction.unfinished` 和本地待同步记录恢复中断购买；不要仅靠订阅的 `currentEntitlements` 恢复消耗品。已 finish 的历史购买不重新发放，余额从服务器读取。[Apple finish 文档](https://developer.apple.com/documentation/storekit/transaction/finish())、[消耗品历史与服务器对账](https://developer.apple.com/documentation/bundleresources/information-property-list/skincludeconsumableinapppurchasehistory)。

购买中切换账号时，原交易仍归原账号；不能发给当前页面的新账号。Sandbox/TestFlight 与生产余额隔离。若有效购买在审批或同步期间遇到 Pro 到期，仍要按原订单正确交付并保留余额，不能吞单。

### 4.2 双余额扣减

- 返回独立字段：`baseLimitMs`、`baseRemainingMs`、`baseResetAt`、`purchasedRemainingMs`、`reservedMs`、`availableMs`、`canPurchase`、`canApply`、`revision`。明确 remaining 是否包含预留；建议 remaining 是账面未消费余额，available 是扣除全部预留后的可用余额。
- `canPurchase` 不依赖余额；`canApply` 依据已确认的会员资格和两种余额的总可用值。旧客户端字段保持原语义，不能把总额度写入 `monthlyRemainingSeconds`。
- 请求按账号、完整生成参数指纹与稳定 request ID 去重。文本、音色版本、语言等影响输出的参数改变时不能误复用。
- 在同一数据库事务中先预留基础、再预留加购，并发设备与预取共享同一锁/原子约束。
- 生成成功后以真实时长结算并释放多余预留；跨月请求使用预留时的明确来源，不能把旧基础额度的释放加到新周期。
- 实际输出可能超过预估时，必须有生成上限及追加预留/失败策略，不能交付后透支或只按预估少扣。低余额时缩短新段落，避免余额大于零却永远无法消费。
- 同一成功请求可恢复取得原音频，不能只做到“不重复扣额”却每次重跑 GPU。失败预留到期释放；释放与晚到成功之间需要原子状态裁决。
- 收费以可恢复的成功结果为准：在成功提交前确认取消/失败则不扣；提交成功后的响应丢失可用原请求取回结果；若最终无法交付，按原来源冲正。播放器暂停不退已交付额度。此处细化旧规范对“超时不扣”和“成功生成扣费”并存时的边界，实现时需同步合同。

### 4.3 退款、兼容与开关

退款按购买批次追踪：撤回该笔交易尚未消耗的加购余额；已消耗部分记退款成本，MVP 不扣其他正常订单、不扣基础额、不制造负余额。通知重复、乱序、退款先于到账以及退款撤销均须幂等处理；补偿记录不能删除原流水。[Apple 退款与消费信息机制](https://developer.apple.com/documentation/appstoreserverapi)。

先上线兼容后端，再发 iOS。第一版只在 iOS 提供购买 UI；所有实际会生成克隆音频的入口必须使用同一余额判定，不能出现 iOS 买到额度、其他入口覆盖或清零。老版本如不能展示加购余额，应引导升级；兼容改造不能打断既有基础额度。

新购买开关和已购服务开关分离：暂停销售后，已支付交易仍应补单，已购余额仍须可使用。不能靠关闭功能把已卖出的权益隐藏。

## 5. 成本核算与候选定价

### 5.1 目前能确定与不能确定的内容

**尚无当前真实单位成本结论。** 本轮检查未取得 GPU 租赁/折旧账单、生产利用率、网关/存储/流量分摊、Apple 实际结算费率和税费。历史长稳吞吐只能帮助设计测量，不能证明当前收费会盈利。现有 [API 成本规划](/Users/xuxuheng/Documents/MyProject/readout-web/docs/international-tts-api-plan-2026-09-08.md) 也记录了这项数据缺口。

上线核算同时看增量成本与包含空闲容量的服务总成本，定价以总成本为主要依据：

```text
每成功生成分钟的服务成本 c
 = 克隆业务分摊的 GPU + CPU/网关/数据库 + 存储/出网 + 运维支持成本
   -----------------------------------------------------------------
               同期实际结算的克隆生成分钟数

120 分钟包按全部用完的服务成本 C = 120 × c
每包平台后净额 N = 不含代收税的实际售价 − 平台佣金 − 退款/折让等
每包服务贡献 = N − C
平台后服务贡献率 = (N − C) / N
```

分母包含基础与加购的成功使用分钟，排除缓存重放、创建、固定试听和失败；这些免费的或失败的操作所耗资源进入分子。共享 GPU 按占用时间及保留容量分摊，不能将整张卡全部费用只摊给加购业务；也不能忽略空闲、热备和失败重试。已含在完整账单内的项目不再额外乘损耗系数。

基础额度成本归属会员业务，加购消耗成本归属加购业务，不能把同一笔成本算两遍。加购预收款和未使用余额单独记录，不把“卖出但尚未使用”直接当作已赚取的服务利润。无有效生成分钟的观察期，单位成本记为不可计算，不能写零。

### 5.2 ¥18 / 120 分钟的敏感性测算

以下单位成本是**情景假设，不是实测**；暂不计税、退款、折让和汇率。15% / 30% 是两档费率假设；15% 需符合并加入相关计划，实际按目标商店合同和结算单核对，不能假定全部地区相同。[Apple Small Business Program](https://developer.apple.com/app-store/small-business-program/)。

| 假设服务成本/分钟 | 120 分钟全部用完成本 | 按 15% 佣金：净额 / 贡献 / 贡献率 | 按 30% 佣金：净额 / 贡献 / 贡献率 |
|---|---:|---|---|
| ¥0.01 | ¥1.20 | ¥15.30 / ¥14.10 / 92.2% | ¥12.60 / ¥11.40 / 90.5% |
| ¥0.03 | ¥3.60 | ¥15.30 / ¥11.70 / 76.5% | ¥12.60 / ¥9.00 / 71.4% |
| ¥0.06 | ¥7.20 | ¥15.30 / ¥8.10 / 52.9% | ¥12.60 / ¥5.40 / 42.9% |

建议以平台后服务贡献率 **至少 70%** 为首版经营目标（不是行业标准或已达成结果）。在上述简化条件下：

- ¥18 包：15% 费率时服务成本须 ≤¥4.59/包；30% 时须 ≤¥3.78/包，即后者约 ¥0.0315/分钟。
- US$2.99 包：15% 时成本须 ≤US$0.76245/包；30% 时须 ≤US$0.62790/包；需用当地成本核算，不直接按人民币换算。
- 若按 30% 佣金、服务成本 ¥7.20，希望达到 70%，所需税前标价至少 `7.20 / (0.70 × 0.30) ≈ ¥34.29`，再选实际可用价格点。此时 ¥18 不能算达到目标。

基础额度也要预算：若真实 `c = ¥0.03/分钟`，每名会员用满 120 分钟的月成本为 ¥3.60；1,000 名全部用满为 ¥3,600/月，平均使用 25% 时按该单位成本约 ¥900/月。年付满用 12 个月约 ¥43.20/人；实际利用率改变时 c 也需重新计算。

### 5.3 上线前后的成本数据

开工即补近 7–30 天真实数据，按全球/中国计算池、语言、成功/失败、冷/热缓存拆分：实际生成音频秒数、推理占用、重试/失败占用、音色创建与试听占用、缓存命中、网关时长、流量和账单。无需为核价向生产 GPU 发送压力流量。

最小日报记录：购买人数/包数、签名有效交易数、到账数及耗时、待补单订单、退款；基础/加购分别消耗的秒数；实际服务成本/分钟；未消费加购余额和履约成本预估。收入先以可得的交易数据作暂估，按 Apple 最终结算校正，不把客户端价格当作最终收入。

**价格决策点**：真实分摊成本和实际结算条件支持目标后采用 ¥18 / US$2.99；不支持时先调候选价格或成本结构，再开放销售，不事后缩减已购分钟数。

## 7. 发布验收

以下均通过才视为 MVP 完成：

1. 基础全满、部分余额、零余额和已有加购额四种状态都能主动购买同一商品；连续两次购买恰好增加 240 分钟。
2. 基础与加购消费顺序正确，月度重置只恢复基础；年付按月发放，购买/恢复/重复通知不额外生成基础额。
3. 基础为 0、加购大于 0 时朗读和解读正常；两者合计不足时停止后续生成并可从购买结果继续。
4. 真实音频时长与账本一致；倍速、暂停、缓存重播和请求重试不重复扣费；失败与超时恢复符合交付状态规则。
5. 两设备并发、预取并发、预留到期与晚到成功、生成跨月均不能透支、双扣或释放到错误余额。
6. 支付成功后杀进程、断网或后端失败，重开会自动补单且只到账一次；取消和等待批准不会提前加额。
7. 换机/重装恢复剩余余额；换账号不会转移额度；同一 Apple 交易不能在两个入口分别到账。
8. 退款/退款撤销及乱序重复通知不会多扣或多发；已消费退款不影响其他正常订单或基础额度。
9. StoreKit 产品与后端配置一致，Sandbox/TestFlight 不污染生产余额；显示本地化真实售价与明确使用条件。
10. 完成成本表，说明数据窗口、分摊方法、目标地区费率和未决项；校准后满足既定售价的经营目标。
11. 保留当前发布版 Kindle/WeRead/Kobo 恢复、播放器失败恢复等核心能力；真实设备完成克隆长文、解读和额度耗尽后继续。
12. 若为首个 Consumable，按 Apple 要求随新 iOS 版本一并提审；准备商品审核截图及可操作账号，不把“商品已建好”当作用户已可购买。[Apple 提交内购说明](https://developer.apple.com/help/app-store-connect/manage-submissions-to-app-review/submit-an-in-app-purchase)。

本次交付为规划。尚未创建 App Store 商品、变更价格或账本，也未修改功能代码。

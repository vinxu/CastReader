# 中国区解读缺少划重点(mark):根因与修复

> 2026-08-18。症状:上传图片 → OCR → 解读,中国区几乎没有 mark,国际区正常。
> 已修复并部署到 CN worker(`castreader-quickread-cn`),等真机验收。
> 补丁存档:`docs/patches/cn-quickread-marks-20260818.patch`(worker 无 git 仓库)。

## 定位方法

先在 worker 的 mark 管线各阶段插诊断日志(`[diag-marks] <阶段> n=<数量> <样式:长度>`),
拿到「模型原始产出 → 场景归一化后 → DeepSeek 修复层后」三段数据,再动代码。
同一份 OCR 文本同时打 CN worker 与国际 worker 做对照。

对照基线(6 段中文论文样本,content_type=paper):

| | 修复前 | 修复后 | 国际区(Gemini) |
|---|---|---|---|
| block_0 | **1** (highlight) | **4** (highlight + number×3) | 4 (highlight + number×3) |
| block_1 | 0–1 | 3 (number×3 完整) | — |
| fast-block0 | 未测 | 4 | — |

## 三个叠加的根因

1. **提示词写死上限,且从不提示编号工具**
   `deepSeekNarrationDiscipline` 里写着 "Choose 1-3 marks",没有任何关于并列项编号的指示。
   遇到「三种编队方式」这类并列集合,DeepSeek 只给 1 个 highlight 概括,而 Gemini 会
   拆成 3 个 number。→ 增加并列集合必须逐项编号的规则(上限放到 5)。

2. **`hasWholeMarkAnchor` 的边界判定对中文根本不成立(影响最大)**
   它用「相邻字符是字母 ⇒ 部分匹配」防止英文 cat 命中 category。但中文每个字都是
   `\p{L}` 且没有分词空白,于是源文「以及任命一个智能体担任统一调度者」里,
   「任命一个…」因为前面挨着「及」被判为片段,整条 mark 被丢。恰好落在标点后的
   短语才活得下来——这就是「中国区几乎没有 mark」的主因。
   → 边界任一侧是 CJK(汉/假名/谚文)时不施加该要求。**此改动对中英双语都做过回归。**

3. **编号序列被当成独立 mark 参与预算竞争**
   `normalizeScenarioMarks`(按字符预算/打分选 4-5 条)与 `normalizeDeepSeekGenericMarks`
   (硬切前 3 条)都会把一串「1、2、3」腰斩成「1、2」,读者看到坏掉的序列。
   → 编号整组保留(上限 6)、不占普通 mark 的字符预算、最终按源文顺序重排 n(杜绝断号)。

## 改动位置(均在 `tools/extract-content.mjs`)

- `deepSeekNarrationDiscipline()`:新增并列集合编号规则。
- `hasWholeMarkAnchor()`:新增 `CJK_ANCHOR_CHAR` 判定,CJK 侧免除边界要求。
- `normalizeScenarioMarks()`:编号整组优先落位 + 不占预算 + 结尾重排 n。
- `normalizeDeepSeekGenericMarks()`:切前 3 条时保护编号组。
- `_diagMarks()`:**临时**诊断日志,验收通过后删除。

## 追加:英文菜单差距巨大的根因(2026-08-18 下午)

用户实拍对照(英文酒水单):中国区只有 3 个圈且**全是数字**($40/14/20),国际区十几处
下划线 + 两组编号。同一张单子做端到端对照,定位到**第四个缺陷**,与前三个独立:

**跨语言判定误杀**:`deepSeekMarkIsDiscussed()` 要求 mark 的词有 45% 出现在旁白里,
以此确认「标了的确实讲到了」。但菜单原文是英文、旁白是中文——英文词根本不会出现在
中文旁白里,于是**每一条英文 mark 都判负被丢**,只有纯数字的 mark(`if (!/[A-Za-z]/)`
提前放行)活得下来。这就是"只剩价格圈"的确切机制。
→ 旁白以 CJK 为主时跳过该校验(无法用词重合验证跨语言)。

配套还放宽了两处提示词:反复述规则限定在旁白(不再连 mark 一起压);条目型页面
(菜单/价目/规格/步骤表)允许最多 5 个 mark,因为那里条目本身就是内容。

**实测(同一份菜单,全页所有块累计)**

| | 修复前 | 修复后 | 国际区 |
|---|---|---|---|
| mark 总数 | 3 | **11–13**(3 次采样) | 18–19 |

差距从 6 倍收敛到同一量级。剩余差异主要是块切分与模型自身波动:国际区更爱把并列条目
成组编号,中国区更多用圈——**密度和正确性已对齐,呈现风格仍有差别**。

**一次失败的迭代(留档避免重走)**:把编号规则加严成「并列条目必须编号、禁止用圈」后
总数反降到 12,还把酒名 "Caravedo Torontel Italia Albilla" 拆成 Italia / Albilla 两个假
编号。规则过严会诱导模型乱切条目,已回退到实测最好的措辞。


## 追加:两区 worker 代码代际不同(2026-08-18 复核)

试图把补丁同步到国际区时发现,两边根本不是同一代代码:

| | 中国区 `/opt/castreader-quickread-cn/current` | 国际区 `/root/castreader/video-pipeline` |
|---|---|---|
| `tools/extract-content.mjs` | 3224 行 | 2218 行(2026-06-23) |
| 场景透镜 / content_type | 有(paper/book/report/contract/study/manual) | 无 |
| `normalizeScenarioMarks` / mark 字符预算 | 有 | 无 |
| `hasWholeMarkAnchor` 逐字锚定校验 | 有 | 无 |
| DeepSeek 纪律段 | 有 | 无(用不上) |
| 核心流程 extractPlan / extractBlock / fast-block0 | 有 | 有 |

这解释了此前所有"为什么两边不一样":**国际区那套 mark 后处理压根不存在**,模型给什么
就画什么,所以它标得多(英文散文 9 处、菜单 18–19 处);中国区新一代加了预算与校验,
在修好四个缺陷之前会把 mark 大量吃掉。

**实测现状(全页累计 mark 数)**

| 形态 | 中国区(修复后) | 国际区(旧代) |
|---|---|---|
| 中文书籍 ct=book | 9 | 7 |
| 英文文章 ct=none | 5–6 | 9 |
| 英文菜单 | 15(11–20 波动) | 18–19 |

中文已反超,英文散文仍偏保守——那是 DeepSeek 每块只给 1–2 个长跨度的风格,提示词调了
四版(2-3 marks 下限、20-45 字跨度上限)都没推动,继续加严反而会诱导它乱切条目(有一次
把酒名拆成两个假编号),已停止调优。

**待决:两区代际收敛。** 建议把中国区这一代整体迁到国际区(它是 provider 无关的,
`llm-provider.mjs` 同时支持 gemini/deepseek),好处是一套代码、场景透镜对全球生效、
四个修复全量覆盖;风险是国际区全体用户的 mark 行为会变(很可能变少但更精准),
需要单独一次带对照测量的部署,不宜顺手做。

## 追加(2026-08-18 晚):skip 边界校验 fail-closed 导致整个 plan 报错

真机(arXiv 论文 PDF,CN 线)复现:toast「解读失败: invalid QuickRead plan: substantive
paragraph N skipped inside streamed block boundary」。

根因:`restoreDeepSeekSubstantiveSkips` 里,DeepSeek 把论文首页的版权声明/作者名单/
equal-contribution 脚注标为 skip;`isClearlySkippableParagraph` 的英文传记式启发式不认,
尝试回塞;段落落在已流式发出的 block0 边界内无法回塞 → **直接 throw,整个解读作废**。
Gemini 线没有这个后处理器,所以只炸中国区。

修复(待部署):不 throw,把该段保留在 skip 列表里(本来就是模型的意图),损失至多一段
narration,换回整场解读。补丁:`docs/patches/cn-quickread-skip-boundary-degrade-20260818.patch`。

连带的客户端 bug(已修,iOS `8d50a86`):plan 失败重试会取消在途 TTS,`TTSError.cancelled`
漏过 `catch is CancellationError` 变成用户可见的「未能完成操作(CastReader.TTSError 错误 0)」。

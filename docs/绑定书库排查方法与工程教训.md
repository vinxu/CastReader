# 绑定书库排查方法与工程教训

2026-07-25/26 一整轮 Kindle / 微信读书排查的复盘。记录**方法**和**踩过的坑**，实现契约见另三份：

- `Kindle登录页自动恢复-跨端对齐指南.md`
- `绑定书库阅读器生命周期-跨端对齐指南.md`
- `绑定书库错误分流-跨端对齐指南.md`

## 一、方法：先埋点，再动手

这轮之前，「点开书变成登录页」这个问题**改过一次没改好**。原因不是难，是**没有观测**——日志里一个字都没有，只能靠猜。

先补观测再改代码之后，几小时内就定位了四个独立缺陷。**这个顺序是这次唯一真正有效的做法。**

### 该埋什么

| 埋点 | 回答什么问题 |
|---|---|
| 落地页分类（`reader`/`auth`/`library`/`other`） | 页面到底去哪了 |
| 服务端重定向逐跳 | 第几跳开始转向 |
| 主 frame HTTP 状态码 | 是被拒绝还是被改道 |
| cookie 指纹（名 + 有效期 + 值的 8 位摘要） | 哪个 token 轮换/消失了 |
| 距上次成功进书 / 加载书架的分钟数 | 是不是时间相关 |
| 进程启动横幅 | 重启了 app，还是同一会话放久了 |
| 实例销毁 | 旧阅读器有没有真的关掉 |

**cookie 值一律不入日志。** 只记名称、有效期和值的单向摘要——足以看出 token 是否变化，不足以还原凭据。这条不能因为「只是调试」而放松。

### 怎么读

日志按启动横幅分段，用 `devicectl` 从 app 容器直接拉，不需要用户截图：

```bash
xcrun devicectl device copy from --device <UDID> \
  --domain-type appDataContainer --domain-identifier com.same.castreader \
  --source Documents/kindle-background-probe.log --destination /tmp/kindle.log
```

注意 `KindleRunLog` 是 `#if DEBUG`。换成 TestFlight/Release 包就完全没有数据，长期收集必须用 Xcode 装的 Debug 包。

### 一个测量陷阱

冷启动后、任何 WebView 发起导航之前，`getAllCookies` 返回空。**每次启动后的第一个快照必定是假的 0。** 真正可信的快照要挂在 `didStart`（那时 network process 已经起来，且请求刚带着这批 cookie 发出去）。

## 二、被数据推翻的结论

记下来是为了**不要再验一遍**。每一条都曾看起来很合理。

| 结论 | 怎么被推翻的 |
|---|---|
| 「登录过期了」 | `at-main` / `session-id` / `x-main` 全程值未变，有效期 350+ 天 |
| 「`max_auth_age` 14 天规则」 | 若是它，恢复时 `at-main` 必然轮换，实测未轮换 |
| 「会话按时间变冷」 | 39 分钟不碰能成功，16 分钟不碰反而失败 |
| 「`session-token` 轮换修好的」 | 让开书成功的那个 token 是更早一次失败时由登录页发的，书架加载并未改动它 |
| 「Akamai 的 `ak_bmsc`/`bm_sv` 过期」 | 失败与成功之间其值未变 |
| 「微信读书串扰」 | 用户交叉验证：播放微信读书后再开 Kindle 不受影响 |
| 「app 侧删了 cookie」 | Google Play 图书解绑曾清空整套共享 WebKit 分区；现已改为仅清本地书架与进度，Google 网页会话必须由单独的显式退出操作管理 |
| 「并发是 13 秒的根因」 | 修掉泄漏后单实例仍 16 秒（真因是 207KB 注入） |
| 「SPA 冷启动天生就要 16 秒」 | 浏览器实测整页 2 秒、323KB / 7 个 JS |

**唯一 100% 命中的指标**：`id_pk` / `id_pkel`（`www.amazon.com`，14 分钟有效期）在则成功、不在则被打回。它们只有碰 Amazon 认证域才签发，而深链开书永远不碰——这解释了「反复点同一本书没用，去书架转一圈就好」。**触发条件至今未解**，留待长期观测。

## 三、四个技术坑

### 1. 每次导航注入 207KB

`pageCaptureBootstrap`（207KB / 4110 行）挂在 `documentStart`，**每次导航都注入**，`didFinish` 之后又完整跑一遍。参照物：Amazon 整个阅读器页面 323KB / 7 个 JS 文件——我们一个脚本占它总量的 64%，还在页面开始渲染之前阻塞执行。

改成按需注入后，**开书从 16~23 秒降到 1~2 秒**。

判据很简单：**注入脚本必须证明自己需要 documentStart**。`metadataBootstrap` 需要（它 patch `window.fetch`，必须抢在站点代码取得引用之前，且只有 13KB）；`pageCaptureBootstrap` 不需要（不装任何早期钩子、自带版本守卫）。

### 2. `deinit` 里的拆除代码永远不会执行

```
ViewModel → webView → configuration → userContentController → ViewModel
```

`WKUserContentController` **强引用** script message handler。这个环自己保证了 `deinit` 不会被调用——而拆除代码恰恰只写在那里。

后果：换书后旧 WebView 继续联网、delegate 继续回调。一分钟点 4 本书就攒 4 个，重定向从 1s 劣化到 13s、31s，最后全部超时。

**教训：WebView 的拆除必须是显式方法，不能是析构。** 并且「暂停/最小化」和「替换/关闭」必须分开——前者要保留 WebView 供后台播放。

### 3. `didFinish` 不是「加载完成」

Cloud Reader 是 SPA，可能一直挂着连接。真机实测：**HTTP 200 在 1 秒到达，`didFinish` 一次都没触发过**，而书其实已经显示在屏幕上了。

之前那些 1~2 秒成功的书只是碰巧 load 事件触发了——**整条链路建立在运气上**。

判定要挂在**响应**（`decidePolicyFor navigationResponse`）上，不要挂在加载完成事件上。

### 4. `safeAreaInset` 进不去 NavigationView

同一个坑栽了两次：先加在每个 tab 的根视图外，再加在 TabView 上，**两次都到不了 `NavigationView`/`NavigationStack` 内部的 ScrollView**，列表底部始终被 mini player 压住。

**唯一有效的位置是 ScrollView 自己身上。** 测量可以在外面做（用同一坐标系量出 player 顶边与 tab 内容底边），但消费必须在里面。

顺带：`MiniPlayerView` 没有固定高度，随内容和动态字体变。**用常量去预留一个内在高度，必然会错**——要测量。

## 四、比技术坑更贵的三个判断错误

### 1. 遮罩制造了它自己要解决的问题

为了盖住白屏加了遮罩 → 于是需要知道「什么时候算加载完」→ 选了 `didFinish` 当判据 → 而它永远不来 → 于是加 30 秒看门狗 → 于是弹出「服务暂时不可用」**而书早就在屏幕上了**。

一层机制引出下一层，最后四层加起来制造了一个原本不存在的故障。**不盖遮罩，这一整串都不存在。**

最终形态：正常加载**完全不干预**（就是个普通网页），只在确实落到登录页时才介入。删掉了 6 类故障分类、5 种处置、静默预算、退避阶梯、看门狗、DOM 就绪轮询、三张终态卡片中的两张。

### 2. 过早下结论

「会话按时间过期」这个说法我讲了三轮，被数据推翻两次才放弃。代价是把用户的复现现场用掉了一次——设计的验证流程里，真正能区分 A/B 的那一步恰好被跳过，测完什么都没得到。

**设计验证流程时，先问：哪一步是唯一能区分假设的？把它排在最前面，并且明确告诉对方不要跳过。**

### 3. 顺手改了没被要求的东西

修 mini player 遮挡时，顺带把它的位置从「距底部 68pt」改成了「贴着 tab bar 8pt」。用户要的是滚动高度，不是位置。结果视觉上贴到了 tab bar 上，还得回滚。

**架构性重构和视觉改动要分开。** 前者可以大，后者必须是用户明确要求的。

## 五、可复用的判断

- **不要为没观测到的故障预先造处置。** 6 类故障里只有 `sessionRejected` 和 `network` 真的出现过，其余四类是凭空设想的。
- **绝不能把网络故障升级成账号问题。** 为一段地铁隧道清掉用户书架，是这类系统里最糟的误判。任何「自动解绑」都要有一次显式确认。
- **改之前先找现成的。** Kindle / 微信读书封面用裸 `AsyncImage`（无持久缓存，每次出现都重下），而项目里 `CachedAsyncImage` + `ImageCache` 早就存在，其他四处都在用。
- **和参照系比。** 「16 秒是不是正常」这个问题，靠讨论得不出答案；打开浏览器测一次就知道整页 2 秒、323KB。**有参照物之前，不要判断某个耗时是否合理。**

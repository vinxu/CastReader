# CastReader 数据采集与隐私边界

> 原则：理解用户如何使用 CastReader，不等于收集用户正在阅读什么。本文是后续任何埋点、日志、分析平台和实验的前置约束。

## 1. 数据分类

### A. 允许进入产品分析的数据

- 随机匿名 ID、内部后端用户 ID；
- App 会话、内容会话、朗读会话、解读会话的随机 ID；
- 平台、App 版本、OS 主版本和设备大类；
- 内容来源与格式枚举；
- 内容长度、段落数、文件大小的分桶值；
- 朗读语言、界面语言；
- 公开音色 catalog 元数据，例如 voice code、tier、gender、accent；
- 结构化操作结果：成功、取消、阻断、失败；
- 结构化错误阶段和经过审核的错误码；
- 延迟、有效播放秒数、完成比例等数值；
- Free / Pro 权益状态、套餐类型和付费触发原因；
- 国家或大区级商店信息（确有业务必要且完成披露时）。

### B. 只允许进入受控业务系统、不进入第三方产品分析的数据

- 登录 email、姓名和头像 URL；
- Apple / Google 身份令牌与 provider account id；
- StoreKit / Stripe 原始交易标识和收据；
- 用户上传到业务服务处理的正文、文档或解读请求；
- 账号删除、退款和客服工单中的身份信息。

这些数据只能在完成业务功能所必需的服务中使用，并按照最小权限、保留和删除规则管理。产品分析只接收内部 ID 或聚合结果。

### C. 禁止采集到分析、日志和崩溃系统的数据

- 文档、网页、书籍和 Kindle 正文；
- TTS `processedText`、timestamps 中的 word 内容；
- AI 解读正文、mark 锚文本和用户输入提示；
- OCR 文字、照片、截图或图片二进制；
- 文件名、书名、章节名和 Kindle DOM；
- 完整 URL、URL query、剪贴板和粘贴文本；
- Amazon、Google、Apple 的账号、密码、授权码和 token；
- 精确位置、联系人、广告标识和设备指纹；
- 服务端原始响应、请求 body 或可能包含以上内容的 debug log。

如果错误排查必须使用用户内容，只能由用户主动选择提交到独立支持流程，明确告知用途和保留时间，不能通过常规埋点静默收集。

## 2. 内容元数据最小化

分析系统只使用分桶值，避免通过极精确特征反推出内容。

建议初始分桶：

- 文本长度：`0–500`、`501–2k`、`2k–10k`、`10k–50k`、`50k+`；
- 文件大小：`<1MB`、`1–5MB`、`5–20MB`、`20MB+`；
- 有效播放：`<30s`、`30s–3m`、`3–10m`、`10–30m`、`30m+`；
- 延迟：`<1s`、`1–3s`、`3–8s`、`8–20s`、`20s+`；
- 完成比例：`<10%`、`10–30%`、`30–60%`、`60–80%`、`80%+`。

如果精确数值对计算 P95 必不可少，可以在第一方受控数据仓库保留数值，但对普通分析工具和人员只开放分桶或聚合视图。

## 3. 身份规则

### 匿名身份

- 使用第一方随机 `anonymous_id`；
- 不使用 IDFA，不做跨 App / 跨公司追踪；
- 不把 IP、设备型号、系统信息组合成指纹；
- `StableDeviceID` 当前承担匿名额度身份，不应未经评审直接复制到第三方分析平台。

额度身份、风控身份和产品分析身份的目的不同。即使底层可以关联，也应由服务端受控映射，不在客户端到处透传同一个长期设备 ID。

### 登录身份

- 统一分析主键是 `backend_user_id`；
- Google sub、Apple user id、OAuth account id 只用于受控认证系统归一化；
- email 和姓名不作为事件属性；
- 登录成功后是否把历史匿名行为关联到账户，需要明确披露、保留规则和删除能力；默认不把匿名历史直接发送给第三方平台做永久 profile merge。

### 订阅身份

- 客户端记录购买意图和用户看到的结果；
- StoreKit、Stripe、Google Play 的交易生命周期以服务端和商店通知为权威；
- 分析系统只需要内部用户 ID、平台、套餐、权益状态、交易状态和必要时间；
- 不上传银行卡信息、完整收据或原始 transaction payload 到产品分析工具。

## 4. 会话和数据最小关联

每个 ID 只服务于一个清晰目的：

| ID | 用途 | 禁止包含 |
| --- | --- | --- |
| `anonymous_id` | 未登录漏斗和留存 | PII、设备指纹 |
| `app_session_id` | 一次前台会话 | 用户内容 |
| `content_session_id` | 串联导入、阅读器、朗读 / 解读 | 文件名、URL、书名 |
| `read_session_id` | 串联一次朗读质量和使用深度 | TTS 文本 |
| `explain_session_id` | 串联一次解读阶段 | 原文、讲解、mark 文本 |
| `backend_user_id` | 登录后跨端统一 | email、provider token |
| `purchase_attempt_id` | 客户端购买流程去重 | 商店收据、支付信息 |

## 5. 客户端与服务端职责

### 客户端适合记录

- 用户界面中的真实意图；
- 内容来源选择与用户取消；
- 阅读器是否展示；
- 音频是否实际开始、暂停和结束；
- 前后台、控制条和恢复行为；
- 付费页触发上下文和购买流程界面结果。

### 服务端适合记录

- TTS、解读、上传和 Pro 接口的请求结果与耗时；
- 统一 user / device / entitlement 归一化结果；
- 商店购买、续订、取消、到期和退款事实；
- 跨端权益一致性；
- 服务可用性和节点质量。

客户端和服务端记录同一链路时使用 request / session correlation ID 去重。客户端网络重试不能生成多次“成功”，服务端幂等重试不能重复计算交易。

## 6. 日志和错误清洗

上线前建立统一清洗器：

- URL 只保留受控 host 类别或来源枚举，不保留 path / query；
- email、token、device id、user id 在普通日志中脱敏；
- HTTP body 和原始响应默认不记录；
- 错误只上传受控 `error_domain`、`error_code`、`stage`、`retryable`；
- TTS、OCR、解读和 Kindle 日志禁止拼接正文；
- Debug 日志不得自动进入 Release 分析平台；
- 崩溃 breadcrumbs 也遵守同样的属性白名单。

## 7. 保留、访问和删除

以下是建议初始规则，最终需要产品、法务和后端共同确认：

- 原始产品行为：最多 90 天；
- 去标识聚合指标：最多 13 个月，用于年度趋势；
- 交易和财务数据：按税务、财务与商店要求保留；
- Debug / 诊断日志：默认 7～30 天；
- 访问权限按产品分析、工程诊断、财务和客服分角色；
- 生产数据访问留审计记录；
- 测试、开发和生产数据完全隔离。

账号删除必须覆盖：

- backend user、认证账户和 session；
- 可识别的产品分析 profile 与关联事件；
- 用户上传内容和可删除业务数据；
- Apple 登录 token 撤销；
- 依法必须保留的数据需要告知保留原因和时间。

当前 iOS 只有“退出登录”，没有完整账号删除链路。账号删除能力、隐私政策和 App Store 隐私问卷应先完成一致性整改，再扩大用户行为采集。

## 8. App Store 与用户透明度

实施任何分析前需要同步检查：

- `PrivacyInfo.xcprivacy` 是否覆盖真实收集与关联关系；
- App Store Connect 隐私问卷是否与代码、服务端和第三方 SDK 一致；
- 隐私政策是否明确数据类别、目的、处理方、保留和删除；
- 是否存在跨 App / 跨公司追踪；如果没有，不接入广告标识，也不触发 ATT；
- 第三方分析供应商的数据处理区域、子处理方和删除能力；
- 用户是否能在 App 内找到隐私政策、账号删除和支持入口。

“产品分析”并不自动等于 Apple 定义的 tracking，但只要把数据用于跨公司、跨 App 定向或与第三方广告数据拼接，就会改变披露和 ATT 要求。CastReader 数据策略默认禁止这类用途。

## 9. 第三方工具选型门槛

本阶段不决定供应商。后续候选工具必须满足：

- 支持禁止采集正文和属性白名单；
- 支持数据区域与保留期配置；
- 支持删除单个用户数据；
- 支持导出原始数据并校验口径；
- 支持 EU / 中国及目标市场的合规需求评估；
- 不默认采集屏幕内容、网络 body、剪贴板或完整 URL；
- 不将数据用于广告画像或供应商自己的模型训练；
- 能关闭自动 session replay，或对 CastReader 永久禁用正文录屏。

对于 CastReader，默认不启用通用 Session Replay。需要观察用户操作时，优先使用无私人内容的受控可用性测试。

## 10. Schema 评审清单

未来每个事件或服务端事实进入开发前，必须回答：

1. 它具体支持哪个产品决策？
2. 没有它是否仍能计算目标指标？
3. 谁产生、谁消费、谁负责口径？
4. 是否可能包含用户正文、URL、文件名或身份信息？
5. 属性是否全部来自白名单枚举？
6. 成功、取消、阻断和失败是否可区分？
7. 是否有幂等键和去重方式？
8. 登录前后是否会发生身份合并？
9. 数据保留多久，用户删除时如何清除？
10. 隐私清单、问卷和政策是否需要更新？

任何一项无法回答，就不进入埋点开发。

## 11. 实施前置闸门

- G0：账号删除、隐私披露与实际数据流一致；
- G1：北极星和指标字典完成产品评审；
- G2：漏斗阶段、分母和排除条件冻结；
- G3：身份关联、保留和访问规则完成安全 / 法务评审；
- G4：清理扩展现存 `url_path`、`page_title`、完整 `referrer_url` 等越界属性；
- G5：完成最小事件规范、逐事件属性白名单和服务端 schema 校验；
- G6：落实事件幂等、真实保留期、账号删除联动和生产 secret 轮换；
- G7：内部数据质量验证通过后，才逐步扩大生产覆盖。

在 G0～G3 完成前，不应为了赶版本直接引入自动采集型 SDK。

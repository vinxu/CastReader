## 一、这次做了什么，以及为什么

产品决策是**首次打开 App 硬登录，全员生效**（含从旧版本升级、从未登录过的老用户）。
竞品 Speechify / ElevenReader 都是硬登录墙且均已过审，它们同样有云端书库 + 订阅同步，
构成 App Store 5.1.1(v) 的豁免理由；CastReader 的绑定书库 + 跨设备 Pro 同步是同类理由。

硬登录墙意味着**登录成为单点故障**：登录挂 = 所有人打不开 App。围绕这个风险做了四件事：

| # | 事项 | 解决的问题 |
|---|---|---|
| 1 | 无网络兜底 | 离线时新用户完全打不开，且不知道为什么 |
| 2 | 登出二次确认 | 登出从「退出账号」升级成「App 打不开」，误触代价剧增 |
| 3 | 邮箱验证码第三通道 | Google 不可达的网络里实际退化成 Apple 单通道 |
| 4 | 购买链 guard 修复 | 硬墙暴露的死循环（见第三节） |

原本还做了「墙上加恢复购买入口」，**后来移除了**：硬登录墙下恢复购买了也进不去 App，
它不解决任何问题，只是噪音；设置页里本来就有。

## 三、硬墙暴露的复合问题（重点）

这是这次风险最高的修复，两端都改了。

**现象**：用户用 Apple 登录后进付费页点「开始免费试用」，被弹回登录页；
登录页因为「已登录」不会自动关闭 → **死循环，无法购买**。

**根因**：Apple 只在**首次授权**返回 email。老用户重新登录、或首次授权时选了
「隐藏我的邮箱」，`account.email` 就是空或 relay 地址。而购买前置条件写的是
「有 email」：

```swift
// 改前：ProManager.purchase / PaywallView 购买按钮
guard AuthService.shared.normalizedEmail != nil else { ... 弹登录页 }
```

硬墙之前这只是「少数人多点一次登录」，硬墙之后所有人都已登录，
这个 guard 就变成了纯粹的死锁。

**修复**：guard 改为 `isSignedIn`。StoreKit / Play Billing 购买本身不需要 email，
email 只决定**跨平台同步何时可用**，不该阻塞付款。

Android 侧有一个等价问题：`freshAccountForPurchase` 对邮箱账号会强制重走 Google
登录（因为没有 idToken），成功后反而覆盖掉邮箱账号 —— 已加 provider 判断短路。

## 四、后端与域名（容易搞错，务必按此理解）

三处 `.com` / `.ai` 各不相同，**不要统一**：

| 项 | 用哪个 | 原因 |
|---|---|---|
| Pro / 额度 / 埋点 API | `castreader.ai` | 客户端既有基址，未迁移 |
| **email-otp API** | `castreader.com` | auth 的正式归属，插件装在 `castreader-content` |
| **发件域名** | `castreader.ai` | **Resend 后台只验证了这一个域名** |
| 法务页 | `castreader.com` | 该站英文无语言前缀，只有 zh 带 `/zh/`；`/pt-BR/` 是 404 |

Android 用 Retrofit 绝对 URL 覆盖 `baseUrl` 实现「只有这两个端点走 .com」：

```kotlin
@POST("https://castreader.com/api/auth/email-otp/send-verification-otp")
```

iOS 用独立常量 `Constants.API.emailOTPBaseURL`。

### 后端插件

`src/core/auth/email-otp.ts`（`castreader-content`）+ `config.ts` 挂载。
**条件挂载**：`resend_api_key` 或 `resend_sender_email` 缺一个就不注册，路由保持 404。

这是刻意设计 —— 客户端把 **404 判定为「功能未开放」**并提示改用 Google 登录；
注册一个会返回 500 的半成品，客户端会显示成「登录失败」，比「暂未开放」更糟。

```
2xx          成功
404          后端未启用（客户端提示「邮箱登录暂未开放」）
400/401/403  验证码错误或已过期
其他          登录失败，请稍后重试
```

⚠️ **不要用 404 表达「邮箱不存在」等业务含义**，客户端会误判为功能未上线。

### 改配置后必须清缓存

`getConfigs` 是 `unstable_cache(..., ['configs'], {revalidate: 3600, tags: ['configs']})`，
Vercel Data Cache **跨部署持久化**，重新部署不管用：

```bash
cd ~/Documents/MyProject/castreader-content && vercel cache invalidate --tag configs --yes
```

## 五、排查这条链路时踩过的坑

按发现顺序，都是真实发生并耗时的：

1. **后端根本没装插件** —— 探测 6 种路由变体确认不是路由名写错（对照组：同 basePath 下 `sign-in/social` 返回 401 而非 404）
2. **`resend_api_key` 从未配置** —— `getEmailServiceWithConfigs` 拿不到任何 provider，整站发不出邮件
3. **配置缓存跨部署持久化** —— 写完数据库、重新部署两次仍读到旧值
4. **发件域名搞错** —— 配成 `@castreader.com`，但 Resend 后台只添加过 `castreader.ai`。
   **`.com` 的 DNS 里确实有 `resend._domainkey`，但 DNS 记录存在 ≠ 已验证**。
   最阴险的是 API 照样返回 `200 {"success":true}`，信却发不出去
5. **Apple relay 邮箱转发** —— 发信域名必须在 Apple Developer →
   *Sign in with Apple for Email Communication* 注册（Domain + Email address 两条）。
   不注册则 Apple 静默拒收，隐藏邮箱用户永远收不到码

另外顺带修掉一个无关的部署阻塞：`readout-web` 连续两次生产部署失败，
根因是腾讯云 COS 释放后 MDX 正文里的死链图片让 fumadocs 构建炸掉
（`[Remark Image] Failed obtain image size`），已把 80 处 URL 迁到 Supabase。
映射规则保结构：旧 COS bucket 名成为 Supabase 的路径前缀。

**遗留**
1. **SPF 加固（可选）**：主域仍是 `v=spf1 +include:_netblocks.m.feishu.cn -all`，
   不含 `amazonses.com`。靠 `send.castreader.ai` 子域 SPF + DKIM 过校验，能送达。
   加固命令（必须 `&&` 串联，同域不能有两条 SPF）：
   ```bash
   cd ~/Documents/MyProject/readout-web && vercel dns rm rec_ff99349a44cd96550d618177 --yes && vercel dns add castreader.ai @ TXT "v=spf1 +include:_netblocks.m.feishu.cn include:amazonses.com -all"
   ```
2. **邮箱账号拿不到 `cms_` 会话**：`/api/mobile-auth/session` 只接受
   `provider = google | apple`（传 `email` 返回 422）。因此邮箱登录用户的
   `verify-apple` / `verify-android` 购买上报会跳过，走既有 pending-sync 降级
   （本机 Pro 立即生效，跨端同步待后续）—— 与中国区手机号账号同一条路。
   better-auth 返回的 token 已存 Keychain / DataStore，后端支持后可直接补换。
3. **Apple provider 未配置**（独立问题）：`/api/auth/sign-in/social` 传 apple 返回
   `404 PROVIDER_NOT_FOUND`，导致每个 Apple 用户 `backendUserId` 恒空、
   `needsAppleRelink` 恒为 true —— 设置页那句「重新登录同步 Pro」用户重登多少次
   都消不掉，根因在后端。Pro 未受影响（`/api/mobile-auth/session` 支持 apple）。
   建议单独排期。

# CastReader 数据策略总览

> 状态：策略定义 v0.1。本阶段只统一业务问题、指标口径、身份链路与隐私边界，不接入统计 SDK，不新增业务埋点。

## 1. 数据工作的目标

CastReader 的数据体系首先回答“用户是否真正获得了阅读价值”，其次才回答“用户是否付费”。数据工作的优先级固定为：

1. 帮助更多用户完成第一次有效阅读。
2. 帮助已经开始阅读的用户持续使用并回来继续。
3. 找到真正与留存相关的产品能力。
4. 在不损害使用体验的前提下，提高合理的付费转化。
5. 识别质量问题和失败链路，让团队知道应该先修哪里。

不把 DAU、打开次数、付费墙曝光次数作为单独的成功标准。这些数字上涨，并不必然代表用户读得更多或产品更健康。

## 2. 北极星指标

### 每周有效阅读用户（WMRU）

**定义：** 一个自然周内，至少完成一次“有效阅读会话”的去重用户数。

有效阅读会话初始定义满足以下任一条件：

- 朗读有效播放累计达到 5 分钟；
- 短内容虽然不足 5 分钟，但播放完成度达到 80%，且有效播放不少于 30 秒；
- 解读首个讲解块播放完成度达到 80%；
- 用户从历史或 Kindle 恢复上次进度，并继续有效播放至少 3 分钟。

这里的“有效播放”只累计音频真实处于播放状态的时间，缓冲、暂停、拖动、生成等待和静音空转不计入。5 分钟是 v0 初始阈值，上线获得基线分布后可以调整，但调整必须给指标加版本，不能直接改历史口径。

### 为什么选择 WMRU

- 它同时覆盖朗读和解读两条产品线。
- 它衡量的是用户获得价值，而不是界面操作。
- 它能连接首次激活、长期留存和付费转化。
- 周维度更适合长文阅读；用户不一定每天读，但可能每周稳定使用。

### 配套指标

- 每周有效阅读会话数；
- 每周有效播放分钟数；
- 每位 WMRU 的有效阅读天数；
- 新用户 24 小时首次价值达成率；
- 已激活用户 D1 / D7 / D30 有效阅读留存；
- 付费用户购买后 7 / 30 天有效阅读率。

## 3. 统一价值链路

```text
进入 App
  → 选择内容来源
  → 内容成功进入阅读器
  → 首段音频或首块解读成功播放
  → 完成一次有效阅读
  → 下次恢复或继续新内容
  → 形成每周阅读习惯
  → 在真实需求下触达 Pro
  → 购买并持续获得价值
  → 续订
```

数据分析必须保留这条顺序。付费页曝光之前，需要知道用户是否已经获得过价值；购买成功之后，需要知道付费是否让用户继续使用，而不是只统计交易完成。

## 4. 三层指标框架

### 第一层：使用价值

回答用户有没有成功读起来、读了多久、是否完成、是否回来。

- 内容导入成功；
- 阅读器就绪；
- 首音成功与耗时；
- 有效阅读会话；
- 内容完成或恢复；
- D1 / D7 / D30 留存。

### 第二层：体验质量

回答用户为什么没有获得价值。

- 文件解析、OCR、网页提取、Kindle 同步成功率；
- TTS 首段生成成功率与 P50 / P90 / P95 时延；
- 解读首块成功率与时延；
- 播放缓冲、异常中断、重试和崩溃；
- 失败后恢复成功率。

### 第三层：商业结果

回答什么价值和什么付费触发真正带来长期收入。

- 不同触发原因的付费页转化；
- 月付 / 年付选择；
- 购买成功、取消、失败；
- 首次价值到购买的时长；
- 购买前有效使用量；
- 购买后使用、续订、取消和退款。

## 5. 身份和会话主链

```text
anonymous_id
  ├─ app_session_id
  ├─ content_session_id
  │    ├─ read_session_id
  │    └─ explain_session_id
  └─ 登录后受控关联 → backend_user_id
                            └─ entitlement / subscription
```

- `anonymous_id`：第一方随机匿名标识，用于未登录阶段的连续漏斗；不使用广告标识或设备指纹。
- `backend_user_id`：登录后统一使用 readout-web / better-auth 的用户主键，不把 Google sub、Apple user id 或 email 当分析主键。
- `app_session_id`：一次前台使用会话。
- `content_session_id`：一次内容从导入到阅读的生命周期，只是随机 ID，不包含文件名、书名或 URL。
- `read_session_id` / `explain_session_id`：分别描述一次朗读或解读会话。
- `entitlement`：跨端服务端权益结果；StoreKit 本地状态负责即时解锁，服务端负责统一归因和后续生命周期。

登录前后的数据是否合并、保留多久、如何响应账号删除，必须先通过隐私与法务评审，详见《CastReader-数据采集与隐私边界.md》。

## 6. 数据决策原则

1. **先定义问题，再定义指标，最后才定义事件。** 不允许因为 SDK 方便就先埋大量点击。
2. **分母必须明确。** 例如付费转化率是“购买成功用户 / 合格付费页曝光用户”，不是“购买用户 / 所有打开 App 的用户”。
3. **用户取消不等于系统失败。** 文件选择取消、购买取消、主动停止需要与错误分开。
4. **客户端行为与服务端结果分开。** 客户端描述意图和体验，服务端描述请求结果、权益和交易事实。
5. **价值指标与收入指标同时看。** 任何付费实验都要观察首次价值率、WMRU、留存和退款率。
6. **不采集内容正文。** 不用牺牲用户文档、照片和 Kindle 内容隐私来理解产品。
7. **跨端同口径。** iOS、Android、Web 和扩展共用指标定义与身份语义，平台只作为分析维度。

## 7. 当前数据基础与缺口

当前已经具备的基础：

- 浏览器扩展已有匿名事件、朗读 / 解读会话 ID、客户端重试队列和 PostgreSQL Raw 事件表；
- `/api/pro/status` 已定义设备、账号、套餐和免费额度的统一合同目标；
- `/api/pro/listen-track` 可以上报朗读消耗秒数；
- iOS 本地可以识别 StoreKit 即时权益；
- `backend_user_id`、email 和 `device_id` 的跨端 Pro 归一化规则已有明确标准。

这些数据目前服务于额度和权益，不等于完整的产品分析。主要缺口是：

- 当前 Raw 表、版本字段和 session rollup 仍以浏览器扩展为中心；
- `.com` 与 `.ai` 的线上 Pro 状态合同和身份解析尚未统一；
- 扩展到 `.com` Pricing / Stripe 的 `funnel_id` 与服务端激活事实尚未稳定闭环；
- 生产分析缓冲、事件幂等、属性 schema、保留和删除仍有可靠性缺口；
- 没有统一的首次价值、有效阅读、来源和失败阶段定义；
- 没有登录前后受控的产品分析身份链路；
- 没有覆盖续订、取消和退款的 Apple 服务端交易事实；
- 没有统一事件规范、属性白名单、保留和删除机制；
- App 内账号删除与隐私披露仍需先完成一致性整改。

因此不能直接把现有 `listen-track` 当作 WMRU 或留存数据，也不能仅凭客户端购买回调计算续订和退款。

## 8. 决策看板顺序

### 每日质量看板

- 各内容来源成功率；
- 首音 / 首块成功率和延迟；
- TTS、解读、播放、登录、购买错误率；
- 崩溃和异常版本分布。

### 每周产品看板

- WMRU 与有效阅读分钟数；
- 新用户首次价值率；
- 来源、模式、语言、免费 / Pro 分群；
- D1 / D7 留存；
- 恢复阅读和完成率；
- 主要漏斗流失点。

### 每月商业看板

- 各付费触发的曝光、购买和净转化；
- 首次价值到付费的时间；
- 购买前后的有效使用；
- 续订、取消、退款和跨端权益一致性；
- 付费实验对留存和退款的影响。

## 9. 推进阶段

### 阶段 0：策略冻结（当前阶段）

- 评审北极星指标和有效阅读定义；
- 评审指标字典；
- 评审漏斗与分析问题；
- 评审身份、隐私、保留和删除规则。

### 阶段 1：最小观测方案

- 只覆盖主漏斗、质量结果和付费链路；
- 输出事件规范、属性白名单和客户端 / 服务端责任；
- 建立开发、测试、生产环境隔离；
- 先在内部或小流量验证数据质量。

### 阶段 2：建立基线

- 连续观察至少两个完整自然周；
- 验证去重、漏数、重复、时区和身份关联；
- 根据真实分布校准“有效阅读”阈值；
- 找出最大的单一流失点。

### 阶段 3：围绕瓶颈实验

- 首次价值低：优化入口、导入成功和首音速度；
- 有效阅读低：优化播放、高亮、内容连续性和失败恢复；
- 留存低：优化历史、继续阅读和跨会话恢复；
- 已获得价值但付费低：再优化套餐表达、触发时机和权益设计。

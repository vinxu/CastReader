# 跨阅读平台的语音生成与播放延迟优化方案

日期：2026-09-18。状态：四阶段客户端实现与本轮逐项验证已完成；最新补充修正已安装，第二轮真机完成曹操连续多页、手动翻页和换声复测。具体短前缀边界仍以回归用例为证据，冷续读和云端首片等待仍有后续优化空间。实测收益、验证范围与剩余限制见 [实施报告](shared-speech-latency-results-2026-09-18.md)。

基线：`codex/mobile-voice-explore-20260914`，HEAD `febfeab` 加微信读书请求身份/中文续读修复。实测证据见 [真机修复验收](weread-clone-playback-fix-2026-09-18.md)。

## 已证实的等待来源

| 实测场景 | 时间 | 原因 |
| --- | --- | --- |
| 晓悦切回曹操 | 10:13:20.418 → 10:13:30.942，10.524 秒 | 仍从 334 字符段落开头生成，到当前读到的第 8 片才恢复播放；之前的音频生成占用时间和额度，但没有播放 |
| 长段预读衔接 | 10:15:06.901 → 10:15:15.173，8.272 秒 | 下一段首片在 10:15:03.488 已返回，但共 7 片收齐后才发布为可播放缓存 |
| 微信读书跨页尾句衔接 | 10:13:52.061 → 10:13:52.177，0.116 秒 | 特殊跨页预热已经逐片接收；尾句结束后立即接管两片已缓冲音频，剩余片继续生成 |

56 条克隆响应均为 200；所记录的调度排队接近 0 ms。不能据此推断后端永不慢，但这两次 8–10 秒等待有明确的客户端编排原因。优先消除已有音频的无效等待与已读前缀的重复生成，不先提高并发上限。

## 影响范围

以下“存在同类风险”是代码路径结论，不代表已经在每个平台测得相同的 8–10 秒延迟。

| 来源/模式 | 当前实现与影响 |
| --- | --- |
| 微信读书朗读 | 普通段间预读整段返回；跨页尾句特殊预热已经增量播放，两套行为不一致。实测已确认延迟 |
| Kindle 克隆音色 | `preloadNext` 明确排除克隆音色进入 Kindle 提前缓存窗口，转到相同的普通整段预读；换音色也使用共用重生成路径 |
| Kindle 常规音色 | 已有按预计秒数选择后续段落的缓存窗口，能提前掩盖部分等待；每段仍需整段返回才公布缓存，未从机制上消除长段等待 |
| Kobo / Google Play 图书 / O’Reilly | 页面提取与翻页各自适配，页面内的 TTS/预读/音色切换复用 `ReadAloudViewModel`，存在同类风险；下一页内容准备还有平台自己的耗时 |
| EPUB / PDF / 网页 / DOCX / 文本 / 拍照 | 共用段落播放编排，存在相同段间预读及切音色前缀重生成风险，是否明显取决于段长、语种、语速和服务耗时 |
| 解读 | 质量讲解块 `prepareSection` 收齐 TTS 后再生成标注时间线；切音色 `revoicePreparedBlock` 重建整块音频和时间线，具有整块等待风险。首块快道另有实现，不能一概认定所有解读首播都等整块 |

Kokoro、社区克隆 `vl_`、私人克隆 `vc_` 都应进入验收矩阵。常规声音快时只是较容易隐藏等待；不能把流式衔接只实现为克隆声音的特例。

## 目标结构

平台适配层提供“可读内容、可验证位置、下一页是否已确认”；统一语音层负责分段、生产、缓存、优先级和播放接续；平台层继续负责 DOM/OCR/PDF 几何及导航，不相互覆盖。

```mermaid
flowchart LR
  A[平台内容与位置适配] --> B[有界语音片段与位置锚点]
  B --> C[共享生成任务与增量缓冲]
  C --> D[当前播放队列]
  D --> E[原有高亮与进度保存]
  D -->|剩余可播秒数| C
```

同一段生成任务同时支持后台预读和前台播放。晋升只改变消费方式和后续请求优先级，不取消后重新发起相同请求。缓存是否“已有可播音频”与生成是否“全部结束”必须是两个独立状态。

## 实施顺序

### 第一阶段：消除有音频却等待整段的问题

- 把普通 `startPrefetch` 接入现有 `onSegmentReady`，逐片交给有界缓冲；读到段落边界时可立即消费已有片段，后续片段继续入队。利用微信读书跨页预热的既有机制，提取共用状态管理，不为每个平台复制一套。
- `moreSegmentsExpected` 表示生产者仍可能供给音频；队列暂空进入等待，不误报完成。生成成功、失败和取消都要收敛该标志。
- 晋升后尾片失败：保留已播前缀，保存未完成子请求/剩余文本，从失败片重试。不得读到已有缓冲末尾便跳到下一段，或重新生成已播前缀。
- 使用会话、内容版本、声音、生产者身份检查回调；暂停、切模式、跳页、切音色都阻止迟到回调自动播放。
- 保留既有请求幂等、额度校验和账号隔离；不要通过重新创建请求规避服务端冲突。

### 第二阶段：切音色仅生成从当前位置开始的内容

- 引入可验证的语音文本范围：句/短片段边界、段内偏移及文本摘要。前台与预读使用同一套确定性分段；音色造成的底层音频拆片不再成为位置主键。
- 切换时优先复用目标音色的有效会话缓存；缓存未命中时，直接从当前已验证句子或短片段起点生成后缀，不从整个段落/章节开头补齐。
- 中文没有可靠词时间戳时可重读当前短句，不能按旧秒数猜字位置；英文等有词时间戳的路径保留准确恢复能力。锚点不确定时保留可解释的恢复选项，不能静默跳文。
- 所有片段记录可追溯的段落位置，高亮仍基于后端 `processedText`，不得把时间戳直接强映射回原文。WeRead 尾句裁剪、Kindle 重排、PDF/OCR 几何也必须保持坐标一致。
- 对用户明确选择切换的语义保持一致：新音频准备完成后 UI 才表示生效；若允许在句尾交接，应明确区分“正在切换”和“已切换”，不能显示新音色却无提示地继续旧声。

### 第三阶段：统一按可播秒数安排预读

- 将 Kindle 常规音色的提前缓存思路泛化，所有来源使用相同的播放时间预算。初始可从约 10–20 秒缓存窗口试验，再按播放倍速、实际生成耗时、网络和内存调整；此数值是待测参数，不是发布承诺。
- 当前段已有安全播放余量时即可为下一段准备首片，不必等当前段全部生成完成才考虑预读；当前片/即将耗尽的队列始终优先。
- 复用现有 `.interactive / .readAhead / .speculative` 调度和克隆前台保护；先保持有界并发，按实际排队数据判断是否需要调整。已经在服务端生成的请求不要仅为重排序而取消重发。
- 暂停、离开阅读器或快速连续换音色时停止新增推测任务，丢弃未发出的旧任务；约束未播放克隆音频的生成秒数，避免用更多扣费换“看起来顺畅”。缓存和背压同时按字节、片段数、时长设上限。
- 下一页内容必须来自平台已确认的可用内容；不能为了预热改变可见阅读位置，或破坏手动翻页确认。

### 第四阶段：解读与服务端按证据跟进

- 解读要让讲解音频与原文标注共同按短块推进；已经播放块的时间线不可被后来的整块重算改写。不能简单先播全部音频、稍后补全部标注，破坏产品的同步要求。
- 优先缩短讲解准备块、逐块缓存；共享底层生产/重试/调度机制，朗读与解读仍保持各自的定位和标注语义。
- 将一次延迟拆为内容提取、鉴权、调度、音色准备、TTS 首片生成、传输、解码、客户端持有、首帧播放。只有测到服务器部分是瓶颈，再优化冷启动、音色准备复用或真正的服务端流式输出。
- 服务端改流式不是第一阶段的前置条件：现有逐片 API 已足够消除“已返回首片却等整段”的等待。

## 验收门槛

以下为建议目标，必须在指定网络、机型、语速与冷/热状态下实测，不把当前样本当作 P95。

1. 下一片已经就绪时，片间/段间实际播放间隙 P95 目标 ≤ 300 ms；“已可解码首片 → 入播放队列”目标 ≤ 100 ms。
2. 无缓存切音色：请求正文不包含目标位置之前无须重读的段落前缀；首播等待随一个短片段的生成耗时变化，不再随之前已读内容长度增长。
3. 正常网络、服务热态下，无缓存首次播放/切音色 P95 先以 3 秒为实验目标；服务器冷启动单列，不能承诺所有情况无等待。
4. 原位置正确、不跳文；中文回退重读范围有界；暂停不自动播放；快速换声、跳页、迟到回调、断网、尾片失败、额度不足均有终态及正确重试路径。
5. 相同子请求重试不重复计费；不因为预读晋升而重复生成；后台额外生成秒数与丢弃比例可统计，内存有界。
6. 来源覆盖 WeRead、Kindle、Kobo、Google Play 图书、O’Reilly、EPUB/PDF；语音覆盖 Kokoro / 社区 / 私人克隆，至少中文和英文，朗读与解读分别验证。真实平台验证与可控生产者/AVPlayer 回归分开记录。

建议先交付第一、二阶段的共用朗读改造及上述回归，再推广预读预算和解读，逐阶段在各平台验收，避免一次替换所有导航与播放器逻辑。

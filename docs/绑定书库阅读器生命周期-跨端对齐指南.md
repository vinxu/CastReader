# 绑定书库阅读器生命周期 · 跨端对齐指南

适用于 Kindle 与微信读书两条 WebView 阅读器。**核心结论：被替换或关闭的阅读器必须显式销毁，不能依赖语言的自动回收。**

## 1. iOS 真实事故

用户一分钟内点开 4 本 Kindle 书，之后：

- 打开一本书从 1 秒变成 13 秒、31 秒，最后 4 个请求全部超时
- 会话恢复逻辑上线后，**同一时刻冒出 4 个独立的恢复流程**，各自去加载书架

日志证据（同一分钟内，同一个请求）：

| 时间 | 并发中的 WebView | 到重定向耗时 |
|---|---|---|
| 21:01:01 | 3 | **31s** |
| 21:01:01 | 3 | **13s** |
| 21:01:20 | 4（其余已超时） | 1s |
| 21:02:23 | — | 书架 3s |

换书后旧的 WebView 仍在后台加载同一个域名，抢连接、被站点节流。

## 2. 根因：一行注册造成的强引用环

```swift
// 注册时：WKUserContentController 强引用 handler
webView.configuration.userContentController.add(self, name: "castReaderKindle")

// 拆除时：写在 deinit 里
deinit {
    webView.configuration.userContentController.removeScriptMessageHandler(forName: "castReaderKindle")
}
```

形成的环：

```
ViewModel → webView → configuration → userContentController → ViewModel
```

**`deinit` 永远不会执行，而拆除代码恰恰只写在 `deinit` 里。** 这个环自己保证了自己不会被拆。

同时还有两条替换路径压根没有任何拆除调用（恢复后替换、清理所有权）。

### Android 对应风险

同类结构在 Android 上同样存在，且不止一处：

| API | 谁强引用谁 |
|---|---|
| `WebView.addJavascriptInterface(obj, name)` | WebView 持有 JS 接口对象 |
| `webView.webViewClient / webChromeClient` | WebView 持有 client |
| `WebView` 被 Activity/Fragment 之外的对象持有 | 泄漏整个 Context |
| 用 Activity Context 构造 WebView | 泄漏 Activity |

**Kotlin 没有 `deinit`，`finalize` 更不可依赖。** 依赖 GC 回收 WebView 是错的：只要还有强引用，它就会继续加载、继续回调。

## 3. 契约：显式 destroy

定义一个**唯一的**销毁方法，把所有拆除动作放进去，**不要放在析构/finalize 里**：

```
destroy():
    1. 取消所有协程 / Task / 定时器
    2. 移除 JS 桥（iOS: removeScriptMessageHandler；Android: removeJavascriptInterface）
    3. 移除注入的 user scripts
    4. 摘掉全部 delegate / client（navigation、UI、scroll）
    5. stopLoading()
    6. 清空订阅（Combine / Flow collector）
    7. 停掉附属 WebView（恢复用的隐藏实例等）
    8. Android 额外：从父 ViewGroup 移除 → webView.destroy()
```

**每一条放弃所有权的路径都必须调用它**，一条都不能漏：

| 路径 | iOS 修复前 | 
|---|---|
| 换书替换实例 | 只调了 `stopAll()`，没碰 WebView |
| 恢复成功后替换实例 | **完全没有拆除** |
| 关闭阅读器 | 只调了 `stopAll()` |
| 清理所有权 | **完全没有拆除** |

落地时建议写一条测试或断言：销毁后 `navigationDelegate == nil` 且 JS 桥已移除。

## 4. 只停播放不等于销毁

原来的 `stopAll()` 停了音频、取消了播放相关任务，看起来「关掉了」—— 但它没有 `stopLoading()`、没摘 delegate。**页面还在联网，回调还在跑。**

分清两件事：

- **暂停/最小化**：保留 WebView（这是 mini player 后台播放的前提）
- **替换/关闭**：必须 destroy

两者绝不能共用一个方法。

## 5. 并发不是唯一的慢因

修掉泄漏后，单实例开书仍然慢。日志显示：

```
21:07:27  load
21:07:28  HTTP 200 landing=reader     ← 网络 1 秒就返回了
21:07:44  didFinish                    ← 16 秒后才完成
```

**HTTP 响应 1 秒到达，`didFinish` 在 16 秒后。** 这 16 秒不在网络上，是 Kindle Cloud Reader 这个 SPA 在 WebView 里冷启动：下载自身 JS bundle、初始化框架、拉取书籍内容、渲染。

所以：

- **泄漏会让它更糟**（多实例互相抢连接），但**不是全部原因**
- 「打开一本书」实际是「冷启动 Amazon 的整个 Web 阅读器」，天然就慢
- 两端都必须有**从发起请求那一刻起的加载态**，不能裸露空白 WebView

进一步优化方向（尚未实施，供两端共同评估）：同一个 WebView 内通过 SPA 自身的路由切书，而不是每本书都做一次完整 document 加载；以及在用户还在书架时预热阅读器外壳。

## 6. 验收标准

1. 连续换 5 本书，任意时刻只有 **1 个** 阅读器 WebView 在联网。
2. 销毁后旧实例不再产生任何日志回调。
3. 关闭阅读器后内存回落（Android: LeakCanary 无泄漏；iOS: Instruments 无残留实例）。
4. 会话恢复同一时刻只有一条在跑，不会每个实例各起一条。
5. 从点击书籍到内容可见，全程有加载态，不出现空白页。

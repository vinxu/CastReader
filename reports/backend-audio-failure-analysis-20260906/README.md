# 六条失败上报的原因分析

本次分析对象是截至 2026-09-06 19:05 北京时间已报告的六条失败，来自五个匿名安装：四个 iOS 安装各一条，同一个 Android 安装两条。它们不是六次服务器崩溃，也不能据此认定六位用户。分析只读日志、事件和发布基线代码，没有改业务代码、部署、发包、重启或额外合成。

**已定位失败处理分支，以及会放大中断和丢失诊断信息的代码问题；尚未取得足以逐条确定底层触发源的异常与请求关联。** 不能把六条一概归为 Kokoro 或克隆模型故障。原始失败上报保留，不因候选误报而删除。

## 逐条结论

以下使用客户端 `occurred_at`，而不是服务端接收时间。客户端时钟并非服务端校时证据，但有助于避免把明显的上报延迟当作发生时间。

| 北京时间 | 场景与实际进度 | 已证实的失败处理路径 | 尚未证明 |
|---|---|---|---|
| 13:14:59 | iOS 1.2.33/build 53，Kindle；上报累计播放 3432 秒 | 自动翻页、下一页提取/激活或恢复播放中抛异常，落入统一 `page_turn_failed`，结束逻辑朗读会话 | 究竟卡在哪个翻页子步骤；是否为取消、页面已变但确认失败或真实页面错误 |

| 18:05:50 | iOS，同版剪贴板英文文本；启动约 70.2 秒后失败，未出首音频 | 与 EPUB 相同的通用 TTS 失败路径 | 70.2 秒不能单独证明某种超时；没有原始异常或响应证据 |

EPUB 那条直到 17:11:37 才被服务端收到，比客户端发生时间晚约 264.8 秒。延迟本身不证明网络断开，但意味着只围绕接收时间查日志会错过可能的现场。两次 Android 的块数是端上最大完成块序号，不能据此保证此前每块都完整播放。

## 为什么一次技术问题会变成停播

### Kindle：导航失败处理直接结束朗读

旧 iOS 在页面边界把下一页导航、提取、激活和重启播放放在同一个 `do/catch`。失败时直接记录 `kindle_page_advance_failed`，显示停在当前页并要求再点播放。这里没有给该次失败保留更细的阶段，也没有单独排除取消。

更明确的一处是翻页前 guard：模式已经改变或同步弹窗可见，都调用同一个失败结束函数。模式改变可能是合法用户操作；即使确有弹窗，也应把后续恢复与业务失败区分开。**此前把第二条直接表述为“确定出现同步弹窗”过于具体，本次修正为“命中模式/弹窗联合条件”。**

已提交的 Kindle 页面确认恢复增强在本轮后端上线中未发包，旧 1.2.33 不会因为后端更新自动获得它。增强也不等于已经证明覆盖这里所有情形。

### iOS 普通 TTS：原始错误被包装，且旧路径没有一次技术恢复

`APIService.request` 的网络错误、HTTP 非 2xx、JSON 解码错误，及 TTS 层的 Base64 错误均可终止生成。普通音色旧请求路径没有针对这些失败的有界恢复。`ReadAloudViewModel` 收到当前段异常后将 `moreSegmentsExpected=false`，设为错误并结束分析会话；已经排队的音频不等于一定立即被清掉，但生成续接已经失败。

诊断上还有一层信息损失：`TTSService` 把普通底层异常转成 `TTSError.generationFailed(error.localizedDescription)`。随后 `analyticsErrorCode` 再用 `error is URLError` 判断网络错误时，原类型已经丢失；它只识别少量 HTTP 文本和英文 `timeout`，许多网络错误、当地语言的超时文案、HTTP 500/502、JSON 和音频解码错误最终都落成 `tts_failed`。**因此 `tts_failed` 本身不是“模型报错”的证据。**

旧 `TTSResponse` 使用自动 Codable：时间戳数组虽然可选，但字段存在且类型错误时仍能使整份响应解码失败，包括有效音频。此缺口已在未发包的客户端增强中修过，但没有原始失败响应，不能说这两次恰好都是坏时间戳造成的。

### Android PDF 解读：整条续读管线异常共用一个终止分支

两条事件已从 `contentFormat=pdf` 确定入口，均在已有多块进度后发生。`startExplain` 先分别处理权益拒绝和 `QuickReadHttpException`，其余 Exception 统一记为 `pipeline_failed / unexpected_error`，然后结束解读状态。这里没有在通用分支前单列 `CancellationException`，所以网络 IO、解析和协程取消等原因会失去区分。

PDF 的 `extractBlock`、TTS、compose 中又有多处 `runCatching(...).getOrNull()`，失败可能变成空块、提前结束当前块或跳块；预取 await 也会吞掉异常。并非每个 TTS/marks 错误都会到达这两条终止记录，**不能把它们直接解释成 TTS 或高亮失败**。真正冒泡到主流程的异常与被吞掉的异常都需要保留阶段和类别，才能解释长内容在哪一步断了。

此外，失败分支未传入文档总块数。统计代码使用 `max(blocksStarted, blocksCompleted)` 作为分母，所以这两条失败都带 `completionBucket=complete`。它只能反映已记入的块进度，不能认证全文播完。`blocksStarted=2` 也不是只启动两块：当前入口仅特别记录首块和第二块，完成序号却持续增长。

## 服务端核查能证明什么

- 固定观察窗口的核心接口 5xx 为 0，Direct 两条旧日志 504 没有新增；它们不是这六条客户端事件的已关联服务器错误。
- 针对两条 iOS 实际发生时窗单独查 4xx，未返回 TTS 4xx。全状态日志查询出现 CLI 重复页、达到结果上限，已去重并明确标记不完整；不能拿这些 200 样本证明对应设备收到完整音频。[窗口记录](vercel-failure-windows.json)、[4xx 查询](ios-4xx-windows.json)。
- Android 全球版旧入口会读取远程 QuickRead 配置，目前 base 为 `https://qr.castreader.ai`，不应只看 Vercel 就认为已覆盖 Android 解读。当前配置不能证明失败时配置完全相同。[入口读回](android-quickread-current-endpoint.json)。
- 对美国 QuickRead 服务既有日志做固定错误标签核查。未取得可与两次 PDF 事件唯一关联的底层异常；日志中很多行没有可用于关联的独立时间戳，不能把缺少匹配日志当作服务完全无错。[QuickRead 日志证据](quickread-log-evidence.json)。
- 六条事件均无 request/trace ID，也没有上传底层异常类或 HTTP 状态。iPhone 当前未连接；已连接 Android 的匿名安装与两次 PDF 失败不匹配，因此没有使用它的日志替代故障设备证据。[设备归属检查](connected-device-attribution.json)。

## 建议的修复顺序

1. 保留底层错误类型、错误码和发生阶段，并用同区 request ID 把客户端、网关及模型/解读工作节点关联起来。只记固定诊断字段，技术细节留在监控，不呈现给用户；不记录正文、音频或密钥。
2. 普通 TTS 恢复不能以损失正文或重复播放为代价：保留已排队音频，从尚未完成的段继续，在未交付音频的请求上进行同区、有界恢复；附属时间戳错误降级。已提交增强需要验证并发包，才能改善旧二进制行为。
3. Kindle 模式切换/取消与真实导航失败分开；导航暂时失败保留恢复状态，先确认是否已翻页，避免重复翻页或让用户承担技术恢复。
4. PDF 解读分别保留 plan、取块、TTS、播放异常，正常取消不计失败；技术恢复不能静默跳过空块或余文。修正完成率分母，避免失败同时被统计成完成。

这次分析没有把候选原因包装成已确认根因，也没有修改生产服务。持续观察能发现复发，但仅凭现有通用事件码继续等 24 小时，无法补回这六次已经丢失的底层异常。

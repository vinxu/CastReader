# 克隆词时间戳：根因与精确对齐隔离验证

日期：2026-09-08。范围：华为 Kindle 实际播放音频、当前克隆 Worker 的
估算算法、两种离线精确对齐方案、扩展/Android/iOS 的实际解析与高亮策略。

**结论：误差在 Worker 生成响应前已经存在。精确对齐明显改善时间位置，但本轮
验证不能作为直接上线许可：Qwen 存在零时长词，英文 CTC 存在数字和语言限制；
生产 GPU 并发、排队及真机端到端延迟尚未验证。线上服务没有修改或重启。**

## 1. 样本与证据边界

- 使用华为本轮实际播放的 23 段克隆 MP3，音频时长 1.296–94.368 秒。
  每段与原始 `text`、返回的词时间戳和音频 SHA-256 对应。
- 不重新生成音频，不读取/修改声纹 prompt，不清账户、不扣新克隆生成额度。
- 生产 Worker SHA-256：
  `97cb920eadf2c467faa284d910d9ea2e1a35540d0e189de4a4cbbb9ff8e21ab6`。
  本地基线 `007104dfc72b6a9b89b0d2c6eeb6bd405b6f1366` 的 Worker 与其一致。
- 独立参考是本机 Whisper Base。**它不是人工词边界真值。** 下文误差是相对该
  参考的差异，不代表已经取得人工盲听验收或总体生产 P95。
- 保留原始 94 秒异常样本，不把末尾低置信度 ASR 重复文字描述为已证实的
  TTS 重复朗读。其尾部仍需单独听测/生成质量诊断。
- 原始音频、全文、逐词结果保存在本 worktree 被忽略的
  `build/alignment-evidence/`，不提交私人声音和账户资料。

## 2. 误差为什么产生

当前 `clone_worker.py` 的调用链：

1. `validate_voice_candidate` 对 x-vector 路径直接返回 `asr=None`。
2. `captioned_speech` 因没有 ASR 对齐结果调用 `estimated_timestamps`。
3. `_speech_timing_profile` 用 20ms 窗口/10ms 步长计算 RMS，判断发声区间和停顿。
4. `_spoken_weight` 按字母数量的 0.62 次幂和数字数量估计每词权重；把整段发声
   区间按权重分配，再贪心地把声学停顿配给预期文字边界。
5. `_allocate_word_group` 没有验证一个短区间能否容纳分配进去的所有词。
   内部“35ms 间隔”只限制寻找附近能量谷，**不是词最小时长门槛**。
6. 最后仅保证时间大致单调、每词至少约 1ms，无法证明时间对应实际发音。

所以它能知道“这里有声音/这里比较安静”，但不知道“这里正在说哪个词”。
短词、停顿、缩写、数字读法和局部语速都会破坏按文字长度分配的假设。
噪声/非正文尾部被判为活动时，整个段落的预期位置也会被拉长。

### 同一个失败样本的重放

实际响应把 `great distance in all directions` 五词放到 **47.090–47.120 秒**，
总共 30ms；在 1.25 倍播放时只有 24ms，正常屏幕刷新必然跳过其中多个词。

用实际 Worker 的纯函数重放解码后的同一 MP3：

- 发声区间被判为 0.62–94.20 秒，共识别出 87 个停顿。
- 同五词被分配到约 48.09–48.13 秒，重现毫秒级挤压和严重后移。
- 另一组 5 个词被分配到 65.42–65.45 秒，每词平均仅 6ms。
- **仅作诊断**，把输入音频临时截到前 33 秒重新估算，该短语回到约 20 秒，
  但仍有不合理短词区间。没有将此裁剪应用到产品。
- 重放用的是 MP3 解码结果，原生产算法用编码前 WAV；有损编码造成能量阈值
  和停顿选择变化，因此重放数值不与原始 JSON 逐字节相同。

原 23 段响应有 46 个小于 35ms 的词区间。已有测试只覆盖 token、单调性、
总时长和双词合成音停顿；未覆盖真实长音频词边界、非正文尾部和停顿过密。
三个客户端都把原始 23 段判为可用词时间戳，说明格式/覆盖率门禁无法发现
音频与时间戳的实质性错位。

## 3. 两种精确对齐对照

Qwen：官方 `Qwen/Qwen3-ForcedAligner-0.6B`，固定 revision
`c7cbfc2048c462b0d63a45797104fc9db3ad62b7`，权重 1,835,544,544 字节，完整 SHA
已核对。使用 `qwen-asr 0.0.6`、PyTorch 2.14.0、MPS float16/eager。

CTC：`facebook/wav2vec2-base-960h`，固定 revision
`22aad52d435eb6dbaf354bdad9b0da84ce7d6156`，MPS float32；声学概率 + 完整 CTC
状态回溯，长音频按带上下文的窗口计算并保留绝对帧时钟。**仅验证英文**。

| 对照 | 与 Whisper 对得上的词 | 起点差异中位数 | P95 | 可用性问题 |
|---|---:|---:|---:|---|
| 旧估算，23 段 | 744 | 380ms | 24,680ms | 长尾造成严重漂移 |
| 旧估算，排除 94 秒样本 | 637 | 310ms | 1,480ms | 正常样本仍有明显误差 |
| Qwen，23 段 | 745 | 60ms | 240ms | 25 个零时长词，影响 12 段 |
| 英文 CTC，21 段 | 714 | 102.5ms | 282.5ms | 2 段数字文本明确拒绝 |

CTC 可处理的同一 21 段，旧估算中位差异为 395ms、P95 25,150ms。
模型对照匹配词数有细微差异；不是全量一一对应的人工标注对照。

异常样本的同五词，Qwen 给出 21.12–22.56 秒，其中 `great` 21.12–21.36、
`distance` 21.36–21.76，与独立识别位置相符。**精确对齐的时间位置有改善，
不等于生成音频的异常尾部已修复。**

Qwen 零时长结果不能通过给 `end` 强加几毫秒来伪造修复。CTC 对 `19th`/`31`
等数字不能擅自删除、改写成字母或省略；需要受验证的发音文本到源文映射。
Qwen 将 `19th` 作为一个词，旧 Worker token 为 `19`+`th`：三端对此仍可建立
文本覆盖，但候选严格一对一适配器会拒绝，必须与声学失败区分。

## 4. 额外处理开销

机器：**Apple M1 Pro，16GB，macOS 26.2**。每个代表样本跑 5 次，表内为
排除该样本第一次后的 4 次中位数。解码 MP3 在计时外；Qwen 包括输入处理和
对齐，CTC 包括声学推理及状态回溯。不含 TTS、HTTP、生产排队或网络传输。

| 音频长度 | Qwen | 英文 CTC |
|---|---:|---:|
| 2.856 秒 | 100ms | 49ms |
| 约 10 秒 | 204ms（10.440 秒音频） | 192ms（10.848 秒音频） |
| 24.912 秒 | 458ms | 570ms |
| 94.368 秒 | 1,461ms | 2,270ms |

Qwen 首轮首次推理 3.58 秒；模型已缓存时新进程加载约 6.67 秒。CTC 已缓存
加载约 0.99 秒。下载权重的时间单独记录，不算进请求处理延迟。
本机观察到的最大 MPS driver 分配量约 Qwen 3.00GB、CTC 2.22GB，包含缓存；
**不能当作 CUDA 显存峰值，也不能外推为 4090 的延迟。**

独立训练机 SSH 被拒绝；只读采样生产美国 4090 时，约 19.7GB 已使用、4.3GB
空闲。因此本轮没有向生产卡加载额外模型、挤占其推理队列或进行并发压测。
**生产 GPU 延迟、与 Kokoro/Nari 共存时的显存峰值、队列 P95 仍是上线前缺项。**

## 5. 实际跨端代码重放

来源固定为：

- 扩展 `37cbdb6`，实际 `TTSService._doGenerate` + normalize + granularity；
  transport 为离线响应，匿名/global fetch 若发生则抛错。
- Android `9ee487a2dfd8e38fc93f65cd360a9c8432a1c1fa`，实际 Moshi adapter +
  `TtsTimestampPolicy.inspect`；临时 host test 完成后移除，仓库保持干净。
- iOS 已提交分支的 `TTSTimestamp.swift` 实际 decoder/quality/language policy，
  用 Swift 编译执行；不是另写一套模拟解析器。

各端回放 68 个输入：23 旧结果、23 Qwen 结果、21 CTC 结果、1 个多余字段负例。

| 输入 | 扩展词级检查 | Android 词级检查 | iOS 词级检查 |
|---|---:|---:|---:|
| 原估算 | 23/23 | 23/23 | 23/23 |
| 原样 Qwen（映射 `text` 为 `word`） | 11/23 | 11/23 | 11/23 |
| 可处理的英文 CTC | 21/21 | 21/21 | 21/21 |

Qwen 的 12 段失败由零时长区间触发。解析成功和词级同步可用是两项独立结果。
测试保留相同音频，扩展每例只调用一次离线 transport，无重新合成或改用别的声线。
这是代码级重放，**不是已部署候选后的三端真实阅读、翻页、取消或弱网验收**。

## 6. 接入前必须处理的兼容问题

1. **响应字段**：Worker 与公共控制面约定四字段
   `audio/audio_format/timestamps/voice_code`；partly 网关可增加两个原文进度字段。
   扩展及控制面会拒绝额外 JSON 字段，`alignment_method/confidence/duration`
   不能直接加进去。多余字段负例已在扩展实际 service 中被拒绝。诊断可放
   内部日志或经明确透传验证的 header。
2. **时钟**：所有词相对同一个最终音频。若在服务端变速前对齐，除以服务端
   speed 一次；设备 playbackRate 不应再次修改返回的时间戳。
3. **词映射**：数字、小数、缩写、合并词、引文、重音符号及重复词需要保持
   正文消费顺序。不能为了满足校验伪造词边界或删掉未对齐文字。
4. **额度**：控制面的 `captionedVoiceCloneDurationMs` 目前读取最大的词尾。
   精确的“最后一个词结束”不同于“MP3 结束”，变更算法会改变扣量口径。
   必须独立以真实音频时长结算，保持一次 reservation/settlement，而不是借
   错误词尾充当音频时长。本轮只审计，没有修改账本和历史额度。
5. **调度**：`schedule_validated_voice` 结束后才执行 `synthesize` 里的时间戳
   分析。目前便宜的 CPU 估算位于 GPU 调度之外；在此直接插入 GPU aligner
   会绕过有界队列。需专用调度、并发上限、截止时间和取消语义。
6. **缓存/重试**：结果 coalescer 缓存 120 秒，fingerprint 包含请求和 prompt
   revision，没有对齐算法 revision。对齐失败后的重试应尽量复用同一次音频，
   避免重复合成/重复扣量；灰度不能混用不同算法的缓存。
7. **语言/失败契约**：现有中日韩保留其句子级协议。本实验不能证明七种字母
   语言或全部十种克隆语言都能使用候选方案。不能将英文 CTC 静默用到其他语言，
   也不能在失配时静默重新输出旧估算时间戳。

候选 `alignment_contract.py` 明确拒绝零时长、非有限、逆序、越界及不一致词序，
不修补时钟；11 项适配/CTC 路径测试通过。它没有接入生产 Worker。

## 7. 保留的验证材料与后续门槛

`build/alignment-evidence/` 包含：

- `manifest.json`、原 MP3、`estimator-replay.json`；
- `whisper-reference.json`、`forced-mps-1.json`、`ctc-mps-1.json`；
- 两种模型 `*-mps-5.json` warm 重复结果、`comparison.json`、`summary.json`；
- `client-fixtures.json`、三个 `*-compatibility.json`、`model-readback.json`。

脚本均在本目录。`probe_extension.mjs` 接收源码根目录/fixture/output；iOS probe
编译实际类型文件；Android probe 临时放入 host test source set，执行时需注入
真实 QuickRead key，并用 `--rerun` 防止外部 fixture 变化被 Gradle up-to-date 缓存。

本轮没有切换生产 Worker、网关或客户端接口，也没有增加商店版本。结束只读回查：
clone PID 568834、Kokoro PID 4137311 仍运行，clone Worker SHA 与起点一致。

建议下一步先选定并补全候选的无效对齐/数字/多语策略，在独立 GPU 做与 TTS
并行的真实队列测试，同时修正音频时长结算依赖；通过后才进入保留原接口的
服务端灰度及三端真实 7–8 页回归。任何生产修改仍须完成变更前/后不可变完整
备份、off-host 私有上传和完整 SHA 回读门禁。

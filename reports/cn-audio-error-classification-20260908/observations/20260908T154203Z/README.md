## 需要通知的变化

国际 Direct 新增 **21 次下游连接关闭**，全部来自 Android 1.0.47，同版本另外有 545 次 200；上轮相同版本为 11 次关闭和 659 次 200。按相同客户端版本的已记录请求比较，关闭占比由 **11/670 = 1.64%** 升至 **21/566 = 3.71%**，约为上轮的 **2.26 倍**。这是一段窗口内的请求级变化，不是用户失败率，不代表唯一受影响用户数，也不能据此认定修改导致故障。

全部 21 个匿名请求键均关联到同区代理的 `cancelled` 结束事件；没有缺失、重复键歧义、上游 HTTP 错误或代理记录的模型错误。Direct 均记录 `downstream_closed / upstream_headers`，耗时 23–3582ms。18 次集中于 UTC 15:02—15:13 内的事件，其中 15:03 的一条仅持续 23ms；不能将所有关闭统一解释成某一个固定超时阈值。

21 个断开请求自身的代理→模型建连耗时中位数 0.262ms、最大 0.524ms。**现有证据指向：后端的额外等待主要发生在建连后、响应头返回前；同期下游关闭增多。** 这只是阶段定位与相关性：不能区分模型排队与生成耗时，不能证明等待变慢导致取消，也不能在没有客户端证据时判断用户操作、客户端逻辑或公网网络是谁最先触发关闭。此轮没有读取客户端行为，也没有为未知原因修改生产。

## 累计与后续

[累计快照](cumulative.json)采用四个完整且连续、不重叠的窗口：发布后约 **2 小时 18 分钟**，CN/US 固定探针各 **27/27**，CN TTS 入口 384 × 200 和 1 × 499，已观察独立 clone 路径 188 × 200；CN provider 已记录 18 次完成（包括最初固定核验），没有恢复分支的线上失败样本。Direct 累计 **3630 × 200、39 次关闭**；Vercel 返回的核心错误记录为 0。

本轮通知的理由是同版本下游关闭占比和后端等待均上升，不能继续简单称为状态无变化。后续保持只读观察，重点查看该上升是否持续、响应头之前的耗时分布，以及是否出现首次真正的供给失败/HTTP 5xx。业务限量和非会员限制没有新增证据，不将这批取消归入业务 429。

本地新增 `rebuild_cumulative.py`，验证时间窗口连续性后累计状态次数，并将请求发生次数与匿名键关联覆盖分开；关联脚本允许 Vercel 仍采集中时先读取已经完成的 Direct 窗口。这些是只读采集/汇总工具变更，不涉及生产服务。

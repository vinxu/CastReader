## 源码解释及可成立的推断

- `tts_service.py:427` 在解析音色及取得 backend 后、分段及模型处理前记录一次生成流开始；它不是 ASGI 请求到达时间。`text_processor.py:332` 的 `Split completed` 只统计构造分段计划，`_split_for_generation` 会先完整收集计划，再开始处理。该窗口分段中位数 0.46 ms、最大 1.67 ms，**不能当作 TTS 推理或整个请求耗时**。
- `_process_chunk` 先在 `tts_service.py:134` 取得全局 4 槽 semaphore，再于 `:167` 取得按语言区分的锁；`kokoro_v1.py:909` 的模型路由记录位于这两个锁之后、音色 adapter 锁及 G2P/模型推理之前。同一语言的模型处理受串行锁限制。该窗口 590 次开始为英语、24 次西语、1 次中文。
- 因而累计分段数先明显超过模型路由数、随后归零，支持当时有模型前积压。这个累计差包含多块请求尚未轮到的后续块，**不是直接采样的排队深度**。按全局 FIFO 强行配对的最大阶段差约 12 秒，只可用于理解量级；不同请求、进程、语言会打破这种配对，不能称为任何一个 504 的真实排队耗时。
- 英语推理路径在异步处理函数中调用同步 G2P / `KPipeline.infer`，架构上可能占用事件循环；现有数据没有当时的事件循环延迟、CPU/GPU 使用率或单块推理时长。**不能据此补写“GPU 打满”或“事件循环卡了 28 秒”。**
- US 稳定代理 `UPSTREAM_TIMEOUT_SECONDS = 180`，连接超时 5 秒；读取入站正文超时 30 秒。它在等待模型响应头期间每 0.1 秒检查调用方连接，调用方断开会取消相应上游任务。Vercel 的约 28 秒调用时长与 US 代理自身 180 秒总超时不是同一个计时器。

## 精确归因的缺口

稳定代理 `web.AppRunner(..., access_log=None, handler_cancellation=True)` 关闭逐请求访问日志，没有保存该四次请求的连接开始、响应头到达、断开或超时记录。模型中间件保存失败/恢复诊断，但没有成功请求的到达、完成、锁等待时长；常规 INFO 日志不带 request ID、PID 或 release，无法精确区分同机 R132/R133 的成功活动。网关侧也未提供可匹配的上游 `x-request-id`。

因此，这批数据能确认存在与超时窗口重合的负载/积压，并显著削弱“模型崩溃或重启”的解释；它尚不能排除 US 连接之前的等待、网络/响应传输问题，也不能宣称已证明四次 504 全由模型排队导致。

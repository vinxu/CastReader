# 9 月 6 日新增核心音频错误：原因定位

本次调查针对截至 **2026-09-06 14:22 UTC** 监控快照中的新增 **4 条 Global TTS HTTP 504** 和 **2 条 iOS player_item_failed**。客户端累计失败由 6 条增至 8 条；4 条网关 504 是另一类服务端记录，不能与客户端失败直接相加为独立用户事故数。此前六条事件的调查见 [上一轮报告](../backend-audio-failure-analysis-20260906/README.md)。

调查结论：**四次 504 的应用终止边界已经定位，约 28 秒的时长与生产预算吻合；同窗 US 模型前存在积压，但每条请求的完整慢因仍缺关联证据。两次 iOS 事件属于本地播放器错误，初始系统异常未保留；另外确认了“失败状态被后续生成回调覆盖，坏 item 仍被复用”的恢复缺陷。当前没有证据把这两组事件连成同一次模型故障。**

本次只读生产日志和已发布代码，运行本地合成夹具探针；没有修改业务代码、生产配置、服务路由，没有部署、重启或调用生产音频合成。以下时间默认 UTC，括号给北京时间。

它们均访问 `api.castreader.ai/api/captioned_speech_partly`，对应生产部署 `dpl_9fnjABFoGBgj2ni2KAgf59Pa2jRc`、后端提交 `e8a755d4ea9602397cad138e6b3bbd3d91f7fa54`。函数执行地均为 iad1，全部热实例，平台上限 300 秒，`hasFunctionCrashed=false`，平台错误码为空，峰值内存 352 / 2048 MB。数据不支持平台 300 秒超时、冷启动或函数崩溃的解释。函数区域只能证明该跳区域，不能证明全链路没有跨境。

发布源码的实际路径：

```text
普通 partly 请求
  → 28 秒总预算（包括上游请求、完整响应体、JSON 解析、重试与退避）
  → 单次 fetch 最多 20 秒；可重试错误退避 0.5 / 1.5 秒
  → 超时或取消抛出
  → gatewayError 将 TimeoutError / AbortError 都转换为 HTTP 504
```

因此 **“总预算耗尽触发应用 504”是高置信判断**：四次执行时长精确贴合这一边界。它不是已捕获的四个 TimeoutError 堆栈，现存日志没有原始异常。

这个 28 秒逻辑可追溯到 9 月 4 日提交 `3f184bf8` / `4d11baeb`，说明是配合原生 partly 客户端约 30 秒首响应期限。不是本次 9 月 6 日才突然增加。若第一轮确实用完 20 秒，500 毫秒退避后，第二轮最多剩约 7.5 秒；这里是代码预算计算，**没有证据证明四条请求各自实际重试了几次**。重试仍访问同一个已选择的上游地址，单纯重试不增加算力；取消若未一路释放计算，还可能增加负担，但目标请求是否出现这种情况未被日志记录。

28 秒是故障终止边界，不能替代对“为什么迟迟拿不到完整音频”的解释。直接延长服务器预算，也可能先撞到已发布客户端 30 秒限制，不能作为充分修复。

详见 [Vercel 元数据和源码核验](vercel/README.md)、[四次执行详情](vercel/request-details.json)。

## 2. 上游为什么慢：有积压证据，尚不能逐请求定因

US 固定窗口 13:23–13:32 的模型日志显示：

- 13:23、13:24 每分钟各 19 次生成流开始，13:29 增至 135 次。
- 13:29:20–13:30:10 有 124 个相同**日志文本前缀**，对应请求输入均为 82 字符。日志只保留前 50 字符，不能证明完整文本完全相同，也不能认定是自然用户、探针、压测或客户端重试。
- “累计已分段块数减累计进入模型路由次数”的差值最高为 29，之后于 13:30:20 归零，与四次请求的等待窗口重合。它包含多块请求尚未处理的后续块，**不是直接测得的队列深度或失败请求数**。
- 源码顺序为全局 4 槽 semaphore → 每语言锁 → 模型路由日志 → 音色 adapter / G2P / 推理。同一语言有串行约束，输入集中时存在等待位置。
- 目标窗口未发现模型失败、OOM 或重启记录；唯一结构化恢复事件是一次成功恢复的英语 G2P token。没有当时 GPU 利用率或事件循环延迟，不能声称“GPU 打满”或“模型挂掉”。

这支持**并发集中、模型前积压是本次慢请求的重要调查方向**，但还不能证明四条 504 全都因排队耗尽 28 秒。按全局 FIFO 假设配对出的约 12 秒阶段差不是逐请求测量，不能用来补齐剩余耗时。

决定性缺口是：US 代理关闭逐请求访问日志；模型成功日志缺 request ID / PID / 发布身份；网关超时分支既不写异常与阶段耗时，也没有在错误响应中保留生成的 request ID。于是无法对齐连接、排队、推理、读体、重试、取消各阶段。US 代理自身总超时为 180 秒、连接超时 5 秒，与网关的 28 秒是不同计时器。

详见 [US 上游调查](upstream/README.md)、[阶段汇总](upstream/aggregate-stage-analysis.json)。

## 3. 两次 iOS 播放器失败：会话事实与已确认恢复缺陷

均为 iOS 1.2.33 / build 53，不同匿名安装标识：

| 会话 | 实际时序 | 能确定什么 |
|---|---|---|
| Kobo 首次引导朗读，英语 af_heart | 13:59:34.096 开始，13:59:36.435 首音频事件，13:59:43.618 失败；累计播放 0 秒 | 开始至失败 9.522 秒。存在首音频事件；不能说完全没收到音频。正常新会话的 12 秒准备超时不能直接解释这个时序。 |
| 历史 EPUB，英语 af_nova，resume=true | 同一会话早在 **9 月 5 日 15:37:11** 开始，前一天已过 300 秒里程碑；9 月 6 日 14:16:31.236 失败，累计 370 秒 | 这是跨日逻辑会话，不是刚刚连续播放六分钟后失败。失败音频的生成时间不明，不能仅按终止时间归因于当天后端发布。 |

首音频事件以客户端 `isPlaying=true` 为依据，而播放器会在 `playImmediately` 后先乐观设置这个值，随后才按真实状态修正。因此该事件不是播放时钟已经推进或用户已经听到声音的直接证明；与累计 0 秒可以共存。

### 初始错误被统一分类，现场原因没保存下来

生产 `onPlaybackError` 把以下四个入口都上报为同一个 `player_item_failed`：写临时文件失败、AVPlayerItem 状态 failed、12 秒准备超时、中途 failedToPlayToEnd。没有保留 NSError domain/code/underlying 链、失败入口、文件状态或失败 segment 的请求 ID。Release 也不写 DEBUG 的 reader-refocus 日志。

所以现在不能判定两次初始故障是坏音频、磁盘失败、媒体准备失败还是恢复后的 item 失效。网络 504 通常走 TTS 错误路径，而这里是已交给本地播放器后的错误路径；两类事件时间不同且无关联 ID，不能强行连接。

### 已确认：失败后有可能无法正确恢复

```text
当前音频 item 失败
  → VM 写入 error；底层失败 item 仍保留
  → 原来的生成任务继续返回片段 / 完成
  → VM 被覆盖为 streaming / ready
  → 再按播放，可能跳过仅在 error 状态下的重生成分支
  → 继续复用 failed item
```

源码中错误回调不取消生成或使 generation epoch 失效；后续 append / 完成回调仍能通过所有权检查并覆盖状态。`loadSegment` 还会在内部播放失败后返回成功。普通播放和锁屏播放路径没有检查、重建失败 item。

本地窄范围探针使用真实失败 AVPlayerItem，验证了 `error → streaming → ready` 时 item 仍保持 failed，重试分支未选中。**这是可达的恢复缺陷，解释“一次技术故障为什么可能变成持续停播”；它不能证明两次生产现场均走到了这一顺序，也不能反推最初为何失败。**

### 音频输入校验也有缺口，但本次坏音频尚未证实

build 53 只要求 Base64 可解码，空字节和 Base64 包裹的非音频内容都可进入播放器。本地 AVFoundation 验证这些输入失败；有效 WAV 即使扩展名为 mp3 也能 ready，因此不能只看后缀宣布格式错误。跨日 EPUB 恢复未核实旧临时文件、未重建 item，也值得修复，但**没有证据显示这次文件确实被系统清理**。

之前提交 `09dcb64` 只覆盖预置音色空音频等部分请求问题，`814030a` / `47f9541` 处理 Kindle；三者都没有修改 AudioPlayerService，也没有修复上述失败状态覆盖。不能把已提交的 Kindle/TTS 修复视为这两次播放器错误已经解决。

会话和源码证据：[匿名会话记录](client/session-evidence.json)、[播放器完整调查及行号](ios-player/report.md)、[状态探针](ios-player/failure_state_probe.txt)、[媒体输入探针](ios-player/local_payload_probe.txt)。本地探针运行环境为 macOS AVFoundation，未冒充受影响 iPhone 上的现场复现。

## 4. 根因定位结果与下一步修复验收

| 问题 | 定位程度 | 应推进的修复与验证 |
|---|---|---|
| 网关约 28 秒返回 504 | 时长、返回层和预算直接匹配；预算到期高置信，原始异常未捕获 | 记录匿名关联 ID、总预算/单次预算/调用方取消、尝试次数、连接/首响应/读体耗时；取消单列，避免所有 AbortError 都记作超时。先获得慢阶段，再调整预算与供给。 |
| 上游集中请求与积压 | 同窗直接日志支持；四个请求无法逐一关联 | 在同区完成代理到达/取消/完成与模型锁等待/推理计时；确定重复请求来源和完整音频身份，再评估重复合成合并、活动朗读优先、排队和独立同区备用。不能无依据认定某类调用方有错。 |
| iOS 失败 item 的恢复 | 已发布源码可达，本地窄探针验证 | 让播放错误状态不被生成进度覆盖；明确当前 item 恢复所有权，按错误类型有界重写文件/重建 item/重新取音频，保持已成功音频和播放位置。验证失败后仍有生成回调、切段、暂停跨日恢复、锁屏 Play 的时序。 |
| iOS 初始失败触发器 | 四类入口合并，具体 NSError 无法恢复 | 增加失败入口、脱敏错误链、字节数/容器、文件存在及大小、segment/request 关联；首音频按实际时钟推进统计。音频校验应触发内部恢复，不能另加高亮或时间戳硬门槛。 |

验证需覆盖“完整音频继续交付及实际播放时钟推进”，不能只看 HTTP 200、健康探针或首音频事件。技术恢复保持所选区域、音色和内容；只有已有业务额度/会员限制承担业务停止语义。调整超时、去重或并发前，要有可回放的延迟/取消/坏媒体夹具和同区测试，避免无依据放大并发或把错误隐藏为成功。

另有 Direct 网关记录 14:17:58.072 的一次 328 毫秒 AbortError → 日志 504。其配置超时是 120 秒，所以不能解释为 120 秒预算耗尽；现存记录也不能证明调用方实际收到 504 或取消原因。它与上述四次持续约 28 秒的 Global 请求分开处理，证据沿用 [监控现场](../backend-audio-iteration-20260906/monitoring/observations/20260906T1422Z/direct-new-error.json)。
